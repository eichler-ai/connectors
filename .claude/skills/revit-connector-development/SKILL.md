# Revit Connector Development

This is the living process doc for building the Revit connector. It's meant to be updated as the process evolves — see "Keeping this skill current" at the bottom. If something here turns out to be wrong or the team starts doing it differently, fix this file in the same PR/session, don't just work around it silently.

## Orientation

- **Design source of truth:** `revit/docs/PRD.md`. Read it (or at least the sections relevant to what you're touching) before implementing anything — this skill covers *how* to build, the PRD covers *what* and *why*.
- **Naming/terminology conventions:** `CONVENTIONS.md` at the repo root. Get the Bridge/Server naming right (see PRD §04) — it's easy to accidentally call the whole connector "MCP Bridge" when you mean the add-in specifically, or vice versa.
- **Repo layout:** `revit/mcp-bridge/` (the add-in, C#/.NET), `revit/mcp-server/` (the broker, Go), `revit/install.ps1`/`revit/install.md` + `revit/install-mac.sh` (Windows and Mac-side installers -- both flat scripts at `revit/`, not a subdirectory), `revit/test-harness/` (live MCP test harness -- see its own README; not the PRD §13 tutorial corpus, which doesn't exist yet).
- **Error/log/notice format:** every JSON-RPC `error.data`, every `notices[]` entry, and every NDJSON log line uses the one diagnostic-record shape in PRD §01 (`severity`, `code`, `source`, `message`, `detail`, `remedy`) — see that section before writing anything that reports an error or diagnostic. `source` values are the module names below (`mcp-bridge.core.execution`, `mcp-server.internal.registry`, etc.), not invented per-feature.

## Testing strategy

Two tiers, deliberately — no mocked-broker-integration middle tier for now. If bugs start showing up specifically at the broker↔add-in wire boundary that neither tier catches, reconsider adding one; don't build it preemptively.

### Tier 1 — unit tests

**MCP Server (Go): unit-test everything, always, TDD-first.** It's pure logic with zero Revit dependency — protocol framing (§05 Framing), tool routing, the instance registry/heartbeat state machine (§05), singleton lock-or-proxy (§05), local/remote path translation (§09). Write the failing test first. Go's standard `testing` package, table-driven tests as the default shape. Run with `go test ./...` from `revit/mcp-server/`.

**MCP Bridge (C#): unit-test everything behind the `Core`/`RevitAdapter` seam.** The add-in's actual Revit-API-touching code (raw `ExternalEvent` plumbing, `DialogBoxShowing` registration, `Transaction` wrapping) is not meaningfully unit-testable — Revit API types are mostly sealed/non-constructible outside a live session. Everything that's *decision logic* should live in `MCPBridge.Core` and be written against interfaces defined in `MCPBridge.RevitAdapter`, so it can be tested with fakes:

- Dialog default-answer policy (§07)
- Failures-API resolution policy — warning vs. error handling (§07)
- Document identity computation — the four-state scheme (§09)
- Cancellation state machine — `pending`/`running`/`busy`/`unrecoverable` transitions (§06)
- Discovery logic — `list_functions`/`search_functions`/`describe_function` reflection + pagination (§08). This one is a genuine bonus: reflection runs against the actual `RevitAPI.dll`/`RevitAPI.xml` files, which are static assets, not a live Revit session — so it's fully unit-testable with those files as test fixtures, no fake/adapter needed at all.

xUnit. Run `dotnet test` scoped to `tests/MCPBridge.Core.Tests/` and `tests/MCPBridge.Discovery.Tests/` as part of the normal dev loop. **Dev-loop economy** (test-quality pass): iterate on ONE TFM (`-f net10.0-windows`) and with `--filter <TestClass>` where possible — the default runs everything twice (net8.0 + net10.0), doubling a ~60s suite for pure-logic changes; run BOTH TFMs once before opening the PR (the dual run has caught a real per-TFM difference, so it stays mandatory at PR time, just not per edit). Pass `RevitApiReference.References` (cached), never `.Paths`, from test helpers — do **not** include `tests/MCPBridge.Integration.Tests/` in that loop; it's currently an empty scaffold (no real test files), superseded by the tier-2 harness below rather than something to fill in.

### Tier 2 — live integration harness

Everything that genuinely needs a running Revit process: `ExternalEvent` actually firing, real transaction commit/rollback, real modal dialogs, the full add-in↔broker↔agent round trip. Lives in `revit/test-harness/` — a Go module that spawns the real `mcp-server` binary and speaks actual MCP JSON-RPC over its stdio (`go test -tags harness`, excluded from `go test ./...`), not a VM/lifecycle orchestrator: it assumes Revit is already running (driven by `prlctl` in this dev environment, or directly on a Windows-native install elsewhere) and skips cleanly if not.

**Anything asserting on what a script actually gets from `ScriptGlobals` belongs here, by construction.** Since PRD §14 shipped, `Document`/`UIApplication`/`UIDocument` are the real Revit types — sealed, non-constructible outside a live session, and in `RevitAPI.dll`, a mixed-mode C++/CLI assembly a plain test host cannot load at all. So "run a script, assert on the result" is a tier-2 assertion now, full stop; tier 1 can still assert everything *compile-time* about scripts (the `ScriptApiDenylist` checks, globals binding) because Roslyn only needs metadata, which it reads straight from the file. **This is still not the PRD §13 validation corpus**, but it is no longer *blocked* on one: the sanctioned-API gap that blocked it is closed.

Not run on every commit by default (it's slow — VM/Revit lifecycle). Run it:
- before merging anything that touches threading (§06), dialog/failure handling (§07), or the discovery reflection path (§08)
- before every corpus regression pass (PRD §13: "re-run the full corpus on every add-in change")
- before cutting a release

## Script API surface — the denylist principle

`ScriptApiDenylist` (`revit/mcp-bridge/src/MCPBridge.Core/Execution/ScriptApiDenylist.cs`) is not a general sandbox — every script already runs inside an ambient `Transaction`/`TransactionGroup` (opened by `TransactionScriptExecutor` before compilation/execution), so a thrown exception rolls back document content for free. The denylist exists only for the API surface where that rollback guarantee doesn't hold. When deciding whether something belongs on it, and which tier, ask one question: **does a thrown exception in the script actually undo this?**

- **Hard-blocked, no override possible** — the answer is no because the problem is structural, not a matter of intent: constructing `Transaction`/`TransactionGroup`/`SubTransaction` would violate the connector's own one-open-transaction-per-document invariant. No confirmation parameter can rescue this; it isn't a risk judgment, it's a conflict with the execution model itself. **The one known exception to that framing is now resolved, and the resolution is worth knowing because it generalizes:** the check is compile-time and cannot know which document a `Transaction` targets, so it also refused a `Transaction` on a document the script had just created — a case Revit genuinely allows. Rather than narrow the check (which would have meant a runtime document-identity comparison, straight into the `ReferenceEquals` gotcha below), the connector took the capability over: it now opens and owns a transaction for every document a script creates, via the `CreateProjectDocument`/`CreateFamilyDocument` script globals (issue #24, PRD §14). **The pattern to reuse: when a guard is over-broad because it cannot see intent, giving the connector the job the script was reaching for is often cheaper and safer than teaching the guard to judge.** The rule stayed unconditional, no new bypass surface appeared, and a bug in the new plumbing breaks a feature rather than a security boundary.
- **Confirmation-gated** — the answer is no because the effect escapes the ambient transaction's boundary entirely: it changes something outside this document's own content — a human's local session (`Close`), the filesystem (`Save`/`SaveAs`), a shared central model other teammates see (`SynchronizeWithCentral`), a physical device (`Print`), or another user's ability to edit (`RelinquishOwnership`). These are legitimate operations with deliberate human-directed intent, so an explicit confirmation parameter on the `execute_script` call is the right mechanism — not a flat block, and not silent prose-only guidance either.
- **Unrestricted** — the answer is yes. Ordinary `Document`/`Element` mutations are covered by the ambient transaction, so no gate is needed.

Run any proposed addition or removal through that test — not "does this feel risky."

**Enforcement detail that matters as much as the list itself**: checks bind to the Roslyn semantic model (actual resolved symbols), never source-text/syntax shape. A syntax-shape first pass had two live bypasses that reached a real Revit document — a target-typed `new Transaction(...)` and a `Document.Close` method-group reference — both closed by binding to symbols instead. Any new denylist rule must do the same, and should be checked against the equivalent bypass shapes (target-typed construction, method groups, aliases) before being considered closed.

**The denylist can only see the SCRIPT's own syntax tree — so OUR OWN public types are a bypass it structurally cannot catch, and this was live-exploitable.** `RoslynScriptRunner.LoadableReferences()` references every assembly loaded in the Revit AppDomain, which includes `MCPBridge.Core.dll` and `MCPBridge.RevitAdapter.dll`. Any `public` type in them is therefore a type an untrusted agent script can name and construct. Confirmed live against real Revit 2027: a script called `UIApplication.Application.NewProjectDocument(...)`, wrapped the result in `new MCPBridge.RevitAdapter.RevitDocumentAdapter(raw)`, called our own `CreateTransaction("mine")`, started it, wrote a `Level` and **committed** — reporting `status: "success"`. `ScriptApiDenylist` never fired, and could not have: the `new Autodesk.Revit.DB.Transaction(...)` happens inside *our* adapter, while `Analyze` only ever walks the script's own compilation. The same shape against the ambient document was stopped only by Revit's own one-transaction-per-document rule — incidental, not a guard we were applying. A code comment on `IDocumentAdapter` had asserted these methods "were never reachable from a script anyway"; it was simply false, and had been since the adapters became reachable.

- **Fix structurally, not with more denylist entries.** Every implementation and every factory for these adapters is now `internal` (`RevitDocumentAdapter`, `RevitUiApplicationAdapter`, `RevitUiDocumentAdapter`, `RevitTransactionAdapter`, `RevitTransactionGroupAdapter`, and `ManagedDocumentTransactions` in Core, with `InternalsVisibleTo` for `MCPBridge.Core.Tests`). A script cannot name what it cannot see, whereas a name-based table is only ever as complete as the last person to remember to extend it — and the denylist is explicitly meant to stay small and Revit-API-focused. The cost was zero: every public member already returned the *interfaces* (`IDocumentAdapter` &c.), which stay public, so nothing outside those assemblies referenced the concrete types at all. That is worth checking first, because when it holds, option (a) is a one-word change per file.
- **A SECOND instance of this same bypass class was found one review round later, while the first was believed fixed — and it is why the general rule below had to be restated.** Round 1 made every *implementation* `internal` and recorded the rule as "interfaces are safe to leave public — a script can name `ITransactionAdapter` and still never obtain one once every implementation is internal." **That is false.** `RevitScriptExecutionHandler` was a public type, with a public constructor and a public `Execute(UIApplication)` whose entire body is `_callback.OnExecute(new RevitUiApplicationAdapter(app))` — i.e. a public factory that hands the now-internal adapter, typed as the still-public `IUiApplicationAdapter`, to **arbitrary caller-supplied code**. A Roslyn script submission can declare types, so the script supplies the `IScriptExecutionCallback` itself, captures the adapter, casts it to `IDocumentCreationSource`, creates a document and calls `CreateTransaction` on it — a real, unmanaged, untracked `Autodesk.Revit.DB.Transaction`, with **no internal type ever named**. Round 1's `internal` fix therefore did not block it, and round 1's own bypass tests (which all assert `new <ConcreteType>()`) kept passing the whole time.
- **The general rule for this codebase, restated correctly: in `MCPBridge.Core` and `MCPBridge.RevitAdapter`, `public` means "script-reachable" — so a public type must neither BE an adapter/adapter-producing type NOR RETURN OR YIELD one, directly or through a caller-supplied callback or delegate.** Default new types there to `internal` and make them public only when something in another assembly genuinely needs them; when reviewing a `public` type here, read its *members' body* for what it passes outward, not just its signature. Round 2's fix took the durable option rather than patching the one instance: the adapter **interfaces** (`IDocumentAdapter`, `IUiApplicationAdapter`, `IUiDocumentAdapter`, `IDocumentCreationSource`, `ITransactionAdapter`, `ITransactionGroupAdapter`, `IScriptExecutionCallback`, the `IRaw*Source` trio) and `RevitScriptExecutionHandler` are all `internal` now too, with `InternalsVisibleTo` threaded RevitAdapter → Core/AddIn/Core.Tests and Core → AddIn/Core.Tests, which pulled `ExternalEventBridge`, `TransactionScriptExecutor` and `RequestDispatcher`'s constructor internal with them. That makes the capability itself *unnameable* from a script, so a third sibling hole via some other public callback/factory pattern cannot recur the same way — worth the extra surface precisely because "just patch this instance" had already been tried once and left a live hole.
- **Round 3 found no third bypass of the transaction boundary itself, and two siblings one rung down from it — so when a class of hole is "closed", look at what sits BESIDE the boundary, not only at the boundary.** Both were live-exploitable and are now fixed and pinned. (a) A script reached the LIVE `ScriptGlobals` with no reflection at all — `((System.Action<string,string>)Publish).Target`, since `Delegate.Target` is public and `ScriptGlobals` must stay public for Roslyn to bind globals by name — and passed it to a then-public `RoslynScriptRunner.RunAsync(..., confirmLifecycleActions: true)`, starting a NESTED run that self-granted the confirmation-gated tier the outer request never asked for. Check 1 was untouched (the nested compile still runs the full `Analyze`), which is exactly why this is worth naming separately: **a "public means script-reachable" audit has to cover the types that decide POLICY, not just the ones that hold capability.** (b) `ActiveDialogContext` was a public static class whose `ClearActive()` turned dialog auto-suppression off mid-run (next real modal dialog wedges the UI thread the script is on — one-line DoS) and whose `DrainRecorded()` erased the §01 record of what was auto-answered before the executor collected it. Both types are `internal` now; the read-only members went with the mutators, because a partial internal-ization invites exactly the "I left the safe half public" reasoning round 1 got wrong.
- **When a fix makes a feature's own plumbing internal, pin the FEATURE too, not just the exploit.** `TestScriptCannotTamperWithDialogSuppression` proves the tampering stopped compiling; `TestDialogsAreStillAutoSuppressed` proves `DialogSuppressionHandler` still auto-answers a real `TaskDialog` and still reports it in `notices[]` across the new `InternalsVisibleTo` seam. Only the second one can fail if the `InternalsVisibleTo` grant is wrong in a way the compiler tolerates.
- Reflection still reaches all of this, and that remains the accepted GUARD-not-sandbox line the denylist already documents. The point of the fix is closing the *plausible-looking, one-line* route, which is the realistic failure mode. Note the accepted line is BIGGER than "a denied Revit member": reflection also reaches the connector's own `ManagedDocumentTransactions`, i.e. commit/rollback authority over every managed document including the ambient one. Same accepted position, but say so where it is documented — `ScriptApiDenylist`'s own comment described only the smaller case until round 3.
- Pinned by `revit/test-harness/denylist_bypass_test.go`, tier 2 by construction: `internal` only means anything against the real assemblies as Revit actually loads them, and `LoadableReferences()` has nothing to reference outside a live Revit process. **Its round-1 cases all assert `new <ConcreteType>()`, which is exactly why the callback-capture hole survived a round undetected** — `TestConnectorCapabilitiesAreNotReachableThroughACallback` now covers that shape specifically. When adding a case here, ask what *shape* of reach it covers, not just which type name it mentions.

## Tools & scripts

### `prlctl exec` reads SYSTEM's environment, not the interactive user's — and that misreads as "the fix didn't take"

`prlctl exec <vm> powershell -Command "[Environment]::GetEnvironmentVariable('MCPBRIDGE_BROKER_MODE','User')"` answers for **`NT AUTHORITY\SYSTEM`'s** User scope, because that is who `prlctl exec` runs as — not for `nicholas`, whose environment is the one Revit actually inherits (via the launcher agent). Confirmed live: that query returned `remote` / `\\Mac\connectors` while the running Revit's own startup log said `MCPBRIDGE_BROKER_MODE=(null) MCPBRIDGE_SHARED_ROOT=\\psf\connectors` and `Mode=Local` — two different accounts' environments, read as one. Restarting the launcher agent (the documented fix for a *stale* agent snapshot) changes nothing here, because the value was never in that user's environment to begin with; you get the identical "nothing changed" symptom for a completely different reason.

- **Believe the add-in's own log, not an env query**: `startup-errors.log` records `raw env MCPBRIDGE_BROKER_MODE=... MCPBRIDGE_SHARED_ROOT=...` followed by `resolved discoveryOptions Mode=... ConnectorRoot=...`, from inside the process that matters. Check that first.
- **To set a variable for the interactive user from SYSTEM**, write the loaded hive directly: translate the account to a SID (`New-Object System.Security.Principal.NTAccount('<user>')` → `.Translate([System.Security.Principal.SecurityIdentifier])`), then `Set-ItemProperty -Path "Registry::HKEY_USERS\<sid>\Environment" -Name MCPBRIDGE_BROKER_MODE -Value remote`. Then restart the launcher agent (so it picks the new block up) *and* Revit (so it inherits it) — both, in that order.
- A machine-scope value can also be supplying a *different*, older answer (this VM had `\\psf\connectors` there, the pre-alias-flip path); a user-scope value overrides it, which is what made setting user scope sufficient.

- **`prlctl`** — Parallels VM/guest control from the dev Mac. `prlctl start|stop|restart <vm>` for VM lifecycle; `prlctl exec <vm> ...` to launch/kill Revit.exe inside the guest once Parallels Tools are installed. Do not use `prlsrvctl` for this — that configures the Parallels service itself, not individual VMs (PRD §13).
  - **`prlctl exec` runs as `NT AUTHORITY\SYSTEM`, not the interactive user** — `taskkill /IM Revit.exe /F` works fine (killing doesn't need a session), but a plain `start "" "...\Revit.exe"` launches Revit into the non-interactive Session 0 (`tasklist` shows it under `Services`, not `Console`) — invisible, no real desktop, no usable UI thread for live testing. Don't attempt `prlctl exec -u <user> ...` to work around this — it prompts for that user's password, which is out of scope to handle through this channel.
  - **`prlctl exec ... -Command "..."` corrupts backslashes and other characters in complex inline strings** — repeatedly observed mangling `\r` sequences (dropping the `r`, sometimes inserting a stray CR), em-dashes, and multi-argument strings with nested quotes (`schtasks /tr "..."` losing its argument entirely). Never build a path or multi-line script as an inline `-Command` string. Instead: (a) for anything beyond a trivial one-liner, base64-encode the full UTF-16LE command and pass it via `-EncodedCommand` — this sidesteps quoting entirely; or (b) write the script to a local file and transfer it, then invoke via `-File`. When transferring file *content* (not the command itself) over stdin, `[Console]::In.ReadToEnd() | [Convert]::FromBase64String(...)` works reliably as long as the destination *path* isn't also passed inline (encode that into the command too, or hardcode it in the transferred script).
  - **There is a hard size ceiling on an inline `-Command` argument, and past it `prlctl exec` just HANGS rather than erroring.** Measured: ~2000 and ~3000-character arguments return in well under a second; an ~8000-character one hung until killed at 120s. So don't try to push a file through in one call. **Recipe that works reliably for any size** — base64 the payload, `split -b 2800`, then one `prlctl exec` per chunk (`Set-Content -NoNewline` for the first, `Add-Content -NoNewline` for the rest), then decode on the VM with `[System.IO.File]::WriteAllBytes(..., [Convert]::FromBase64String((Get-Content ... -Raw)))`. **Always compare the byte length on both sides before trusting the result.** Throughput is roughly 2.8KB/call at ~1s/call, which is fine for scripts and zipped payloads (a 131KB DLL zip = 47 chunks; a 331KB source zip = 119 chunks, ~4 min) and hopeless for a 70MB build output — zip and strip `bin`/`obj` first, or find another route. This is the practical way to get a build onto the VM when the shared folder is unreachable from SYSTEM (below) *and* the local copy is stale.
  - **In `zsh`, an unmatched glob is a hard error that breaks `&&` chains** — `rm -f chunk_*` when no chunks exist aborts the rest of the line, silently skipping the `split` that was supposed to create them, and you get a confusing "0 chunks" much later. Use `rm -f chunk_?? 2>/dev/null || true`, or separate the statements.
  - **A `Where-Object { $_.CommandLine -like '*pattern*' }` process filter run via `prlctl exec -Command` can match its own process** — the invoking `powershell -Command "..."` process's own command line contains the literal filter pattern string, so a broad pattern (e.g. `*launcher-agent.ps1*`) matches and kills/lists the diagnostic command itself, not just the real target. Anchor the filter on something that can't appear in your own `-Command` string (e.g. `-and $_.CommandLine -notlike '*Get-CimInstance*'`, or a flag unique to the real process like `*-WindowStyle Hidden*` if your own command never uses it).
  - **To relaunch Revit into the actual interactive desktop session**, use the **launcher agent** (below) — not the old one-shot `/it` Scheduled Task technique. The `/it` approach (reusing the logged-in user's session token from a foreign SYSTEM-context task) was the documented mechanism through most of this project but proved unreliable in practice: an `/it` task can report `Last Result: 0` (success) while producing zero actual effect, and this got *worse*, not better, over the project's life. Kept here only as historical context if the launcher agent itself is ever unavailable:
    ```
    prlctl exec <vm> cmd /c "schtasks /create /tn LaunchRevit /tr \"cmd /c set MCPBRIDGE_BROKER_MODE=remote&& set MCPBRIDGE_SHARED_ROOT=\\\\psf\connectors&& start \\\"\\\" \\\"C:\Program Files\Autodesk\Revit 2027\Revit.exe\\\"\" /sc once /st 23:59 /ru <username> /it /f"
    prlctl exec <vm> cmd /c "schtasks /run /tn LaunchRevit"
    prlctl exec <vm> cmd /c "schtasks /delete /tn LaunchRevit /f"
    ```

### The launcher agent — starting/stopping Revit autonomously

A persistent PowerShell script, version-controlled at `revit/dev-tooling/launcher-agent.ps1` (issue #26 — previously it existed only as a hand-edited file on the VM, never reviewed) and deployed to `C:\dev\launcher-agent.ps1`, runs continuously inside the interactive user's **own** logon session (started via a normal `AtLogOn` Scheduled Task for that same user — no SYSTEM-context impersonation involved) and watches `C:\dev\.launcher-signals\` for drop files. **To deploy a change: copy the repo file over the VM path and restart the agent** — see the stale-snapshot gotcha below, it applies to the script's own code just as much as env vars. `revit/dev-tooling/register-launcher-agent.ps1` (also now version-controlled) recreates the `MCPBridgeDevLauncherAgent` AtLogOn task from scratch if it's ever lost.
- Drop a `*.close` file (any name/content) → it closes Revit gracefully (`CloseMainWindow`, bounded wait) and force-kills `Revit.exe`/`RevitWorker.exe`/`RevitAccelerator.exe` only for whatever's still running afterward (issue #26 — a bare force-kill stamps the open `.rvt` "in use" *inside the file*, which then blocks the next launch against that same path with a modal prompt; this was the single most expensive item in a measured dev-loop cycle).
- Drop a `*.launch` file (content = optional document path, empty = no document; a 2-line form's line 1 is an alternate Revit exe path, line 2 the document) → it starts Revit. A **three-line** signal (issue #26, "pristine-fixture-copy-per-launch") keeps line 1 as the same optional exe-path override and treats line 2 as an untouched source, line 3 as the working copy actually opened — copying line 2 → line 3 fresh on every launch, so a `*.close` taint (or any other accumulated state) in the working copy never carries forward. This copy is a precondition, not best-effort: if Revit is still running (it could be holding a lock on the destination), the source is missing, or the copy itself fails, the launch is **aborted** rather than falling through to open whatever's already at the destination — see the script's own comment for why silently opening a possibly-tainted file was worse than not launching. A launch that opens a document also schedules a forced broker restart ~75s later (issue #26, "forced reconnect") to sidestep the one-shot register-snapshot race described below, rather than waiting for a caller to notice `documents: []` and force one by hand; a `*.close` cancels any reconnect a prior launch scheduled (nothing left to resync for), and a blocking `*.runexe` (below) drains a pending reconnect immediately before it blocks rather than risking it firing mid-run or right after. `*.close` is handled before `*.launch` in every polling iteration, specifically so a launch-then-close dropped moments apart can't land in the wrong order within the same tick.

Because the agent runs natively in the user's own session (not injected from outside), `Start-Process` from inside it lands in the real interactive desktop — this is what makes it more reliable than the `/it` technique. Drive it like this:
```
prlctl exec <vm> powershell -Command "New-Item -ItemType File -Path 'C:/dev/.launcher-signals/x.close' -Force | Out-Null"
# ... wait for Get-Process Revit to return nothing ...
prlctl exec <vm> powershell -Command "New-Item -ItemType File -Path 'C:/dev/.launcher-signals/x.launch' -Force | Out-Null"
```

The same session-scoping reasoning extends to anything else that needs to land in the interactive user's own context, not `prlctl exec`'s default SYSTEM one — the agent script now also handles:
- `*.startbroker` (content = optional `mcp-server` exe path, defaults to the dev worktree binary) — starts the broker **from inside the launcher agent's own session** so its `broker.json` writes to `nicholas`'s profile, not SYSTEM's. Starting the broker via a bare `prlctl exec Start-Process` writes `broker.json` to `C:\WINDOWS\system32\config\systemprofile\AppData\...` instead — invisible to the add-in, which reads from the interactive user's profile — with no error, just a `broker discovery failed`/connection-refused loop that looks identical to a dead broker. Route broker starts through this signal, not a bare `prlctl exec`. **Issue #26, "broker-lock-race guard":** the singleton lock (PRD §05) is a real OS-level exclusive lock — whichever process asks first wins, unconditionally — so a harness-spawned secondary that's still alive and already retrying its own lock acquisition can beat a freshly-started replacement primary to it (the fresh one has to pay full process-launch cost before its first `AcquireLock` call). Only a process that WINS the lock ever writes `broker.json` — a secondary writes nothing — so after starting, the agent polls and reads whatever `broker.json` currently says (not just "did it just get rewritten"; a pre-existing impostor's file may never change during the poll) and treats it as authoritative once the pid it names is confirmed to belong to a still-live process. If that pid isn't the process we just started, it's killed (only after confirming it's still alive and its name looks like a broker, to avoid a PID-reuse mis-kill) and the attempt retries (up to 3). Same guard now runs after the forced-reconnect restart above too, which is exactly where this race is most likely to bite (right after a Revit/broker restart, with a stray secondary from an earlier backgrounded `go test -tags harness` run still sitting there).
- `*.sendkeys` (content = a `SendKeys` string) — **does not currently work.** Confirmed live: even from inside the launcher agent's own interactive session, `EnumWindows` finds **zero visible top-level windows anywhere on the desktop** — not just none owned by Revit, none at all, including Explorer's own taskbar. This VM's `AtLogOn`-triggered "interactive" session is not attached to a window station `EnumWindows`/`SendKeys` can see into, even though the session shows `Active`/`console` in `query session` and processes launched from it (Revit included) run and respond normally. UI automation (simulating keystrokes/clicks to drive dialogs, "File > New", etc.) is a dead end in this environment as currently configured — don't spend time on it; if a scenario genuinely needs it (e.g. testing against a truly unsaved/new document), the two options are: build a document via a Revit journal-file replay (Revit's own scripted-input mechanism, not Windows UI automation — not yet built in this repo) or ask the user to drive it manually.

**But you CAN see the screen, even though you can't drive it — `prlctl capture "<vm>" --file screen.png`, then just read the PNG.** The "UI automation is a dead end" note above is about *driving* the UI; it is not a reason to work blind, and treating it as one costs hours. A screenshot is the fastest way to resolve any "Revit is running but nothing is happening" state, and it repeatedly beat log-archaeology in practice: two separate blockers in one session (a "File Opened By Another User" prompt, and a link-reload warning dialog holding a document open) were invisible in every log we had and obvious in one capture. Take one *early* whenever a live step stalls, before theorising. The right escalation is therefore: **capture to see what's on screen → identify the exact control → ask the user for that one specific click.** That's a few seconds of the user's time, versus an unbounded hunt. Note a modal dialog can be hidden *behind* another window (Revit's trial splash hid one from the capture until it was raised), so if the journal says `ADialog::doModal start` with no matching dismissal, believe the journal over an unremarkable-looking screenshot.

**Gotcha — `DisallowStartIfOnBatteries` silently wedges every start attempt in `Queued`.** The `MCPBridgeDevLauncherAgent` task was registered with Task Scheduler's DEFAULT power settings, which include `DisallowStartIfOnBatteries = True`. Parallels passes the Mac's battery state through, so whenever the MacBook is on battery, `Start-ScheduledTask`/`schtasks /run` report success (`LastTaskResult: 0`) and the task sits in state `Queued` forever, never launching the agent. This is indistinguishable from the interactive-token flakiness described below — same symptom, completely different cause — and it cost a live-validation session before it was found. **Check `(Get-ScheduledTask -TaskName '<name>').Settings | Select DisallowStartIfOnBatteries` before concluding a task is a token problem**, and fix it once with:
```powershell
$s = New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries -MultipleInstances IgnoreNew -ExecutionTimeLimit ([TimeSpan]::Zero)
Set-ScheduledTask -TaskName 'MCPBridgeDevLauncherAgent' -Settings $s
```
The agent started immediately afterwards. Worth applying to any dev task on this VM, since none of them should care about battery state.

**Gotcha — it's a long-lived process, so it has a stale environment snapshot.** The agent process was started once (at logon) and never re-reads the registry. Any `[Environment]::SetEnvironmentVariable(..., 'User')` change made *after* the agent started is invisible to every Revit process it subsequently launches, because `Start-Process` inherits the *agent's own* (stale) environment block, not a fresh one. **After changing any `MCPBRIDGE_*` env var (or any env var Revit/the add-in reads), you must restart the launcher agent itself**, not just relaunch Revit through it — otherwise you'll get identical, confusing "nothing changed" symptoms indistinguishable from the fix not having worked. Restarting it non-interactively is *sometimes* unreliable (`Start-ScheduledTask`/`schtasks /run` can leave the task sitting in `Queued` state rather than actually running — the same class of flakiness as the old `/it` mechanism, for the same underlying reason: a foreign-context trigger into an `AtLogOn`/interactive-token task doesn't reliably attach). **It is worth trying first, though — it has since worked cleanly several times in a row**: kill the old process, `Start-ScheduledTask -TaskName 'MCPBridgeDevLauncherAgent'`, then confirm the task reports `Running` *and* that a NEW pid exists. Don't trust the task state alone. If it doesn't take, fall back to a genuine interactive trigger: ask the user to click **Run** on the task in Task Scheduler's GUI, or to run `powershell -File C:\dev\launcher-agent.ps1` themselves from an already-open interactive shell.

**Never clean up scheduled tasks with a wildcard.** `Get-ScheduledTask -TaskName '*MCPBridge*' | Unregister-ScheduledTask` looks like tidy housekeeping and is a live grenade: the VM accumulates long-lived dev tasks under that prefix, and one such "cleanup" destroyed 13 of them — including `MCPBridgeDevLauncherAgent`, the AtLogOn registration the entire launcher-agent mechanism depends on. The running process survived (so nothing failed visibly) and it would only have broken at the next logon. Delete tasks **by exact name, only the ones you created this session**. `MCPBridgeDevLauncherAgent` can be recreated from `register-launcher-agent.ps1`; the others generally can't be, since nothing in the repo defines them.

**Verify a restarted agent is running the code you just deployed, not just that a process exists.** The agent is a long-lived script read once at start, so "a new pid appeared" says nothing about *which* version it loaded. Drive one signal through it and check the effect — a `*.launch` naming a deliberately nonexistent exe is a good probe, because it exercises the parse-and-log path end to end while being incapable of starting anything. (`C:\dev\launcher-agent.log` records every consumed signal, its parsed exe/doc, the launched pid, and any `Start-Process` failure.)

**Drop every signal file ATOMICALLY — write it under a non-matching name, then rename it into place.** The agent polls for `*.launch`/`*.close`/`*.startbroker`/`*.sendkeys` every 2s and consumes whatever it finds *immediately*. A signal dropped in two steps — create the file, then write its content (`New-Item` followed by `Set-Content`, or any non-atomic write from outside the session) — can be observed in between, i.e. **empty**, and an empty `*.launch` means "launch Revit with no document." So:

```powershell
# WRONG -- the agent can consume this between the two statements
New-Item -ItemType File -Path 'C:\dev\.launcher-signals\x.launch' -Force
Set-Content -Path 'C:\dev\.launcher-signals\x.launch' -Value $docPath

# RIGHT -- content is complete before the name the filter matches ever exists
Set-Content -Path 'C:\dev\.launcher-signals\x.tmp' -Value $docPath
Rename-Item  -Path 'C:\dev\.launcher-signals\x.tmp' -NewName 'x.launch'
```

This one is nasty because **the failure is completely silent and mimics an add-in bug**: Revit really does start, the add-in really does load and connect, and `register` really does report `documents: []` — which reads exactly like broken document tracking in the Bridge or the Server, not like a signal that lost its payload before anyone read it. It cost a full live-validation session (chasing a suspected regression in a Revit-2025-support PR that turned out to be entirely innocent). **The decisive check is Revit's own journal, not anything on our side**: `Select-String -Pattern '<YourDoc>' journal.NNNN.txt`, plus `(Get-CimInstance Win32_Process -Filter 'ProcessId=<pid>').CommandLine` — if the document path isn't on Revit's command line, Revit was never asked to open it and no amount of debugging the add-in will explain it. The agent now also has a **two-tier settle guard** plus a `C:\dev\launcher-agent.log` recording every consumed signal, its parsed exe/doc, the launched PID, and any `Start-Process` failure (which it previously swallowed with no trail at all) — check that log first when a launch doesn't do what you asked. The two tiers matter: a signal *with content* is consumed after 1s, but an **empty** one waits 15s, because an empty `*.launch` is genuinely ambiguous — it means both "launch with no document" (legitimate, documented) and "the payload hasn't landed yet". A flat 1s wait was measured still failing: a create-then-write drop with a 3s gap got consumed at the 1s mark with zero lines and launched Revit with no document — the original bug reproduced by its own fix. Verify a guard like this against a gap *longer* than the timeout, not just a tight one, or you'll confirm only the case that was never broken.

**Do not treat "no MCPBridge log output yet" as ambiguous** — if you changed a `MCPBRIDGE_*` env var, restarted Revit, and still see stale behavior, check the *first* line of `connection.log` (`RunConnectionLoop starting. Mode=... ConnectorRoot=...`, logged unconditionally as the very first statement) before assuming the fix is wrong. If it still shows the old `Mode`/`ConnectorRoot`, the launcher agent — not your code change — is the thing that's stale.

### Add-in deployment location — only two are valid, and Revit fails silently on the wrong one

Revit's `AddInLoader` recognizes exactly two manifest locations per version, and treats everything else as if it doesn't exist — **no error, no dialog, `OnStartup` simply never runs**:
- All-users: `C:\Program Files\Autodesk\Revit\Addins\<version>\`
- Per-user: `%AppData%\Roaming\Autodesk\Revit\Addins\<version>\`

**`C:\ProgramData\Autodesk\Revit\Addins\<version>\` is NOT a valid location**, despite looking like a plausible "all-users" path and despite `xcopy`/manual deployment there succeeding without complaint. During first live-wiring validation, every rebuild/redeploy cycle for several hours targeted `ProgramData` while a stale, hours-old copy of the add-in sat undisturbed in the per-user `Roaming` folder from an earlier test — Revit loaded only the stale `Roaming` copy every time, so identical symptoms (the same `FileNotFoundException`) persisted across multiple genuinely-different code fixes, each of which was actually correct but never reached the binary Revit was loading. **Pick exactly one of the two valid locations and always deploy there** — don't let both accumulate copies, since a stale one will win silently if the fresher one happens to be invalid or the deploy to it partially failed.

To confirm which manifest location(s) Revit actually recognized on a given launch, check its journal (`%LocalAppData%\Autodesk\Revit\Autodesk Revit <version>\Journals\journal.NNNN.txt`) for a line like:
```
Add-in manifest file from: <path>\<name>.addin, won't be loaded. All-users Add-in manifest files must be installed to: C:\Program Files\Autodesk\Revit\Addins\<version>
```
If that line appears for the path you just deployed to, nothing else about the deploy matters until the location itself is fixed.

### Verifying you're actually debugging the binary you just built

Don't assume a redeploy landed where Revit will load it from, or that Revit is running the DLL you just built — verify it directly, every time symptoms don't match a code change:
- **Log the loaded assembly's own identity as literally the first statement of `OnStartup`**: its `Assembly.Location` and `File.GetLastWriteTime` (or `FileInfo(...).LastWriteTime`) against that path. Compare against the build output's own timestamp before treating any subsequent log line (or its absence) as meaningful. A "diagnostic that should fire but doesn't" is otherwise indistinguishable from "the diagnostic isn't in the binary Revit actually loaded."
- **File locks can silently defeat `xcopy /Y`.** `RevitWorker.exe`/`RevitAccelerator.exe` (not just `Revit.exe`) can hold a lock on a deployed DLL even after `Revit.exe` itself is killed. Kill all three before redeploying, and `del /F` the target before `xcopy` so a lock shows up as a loud failure instead of a silent no-op.
- **A source edit made on the Mac side is not automatically visible to a VM build.** When the VM is building from the shared folder (`\\psf\connectors`) directly, edits are visible immediately. But if the shared folder isn't reachable (see below) and the VM is instead building from a *local copy* (e.g. `C:\dev\revit`, made via a one-time `robocopy`), that copy is a **snapshot, not a live mirror** — every subsequent Mac-side edit must be explicitly re-synced before the VM will build it. A `dotnet build` against a stale local copy succeeds, produces a real DLL, and gives zero indication that the source it compiled doesn't match what you just edited. **After any edit, when building from a local VM copy: grep the actually-deployed DLL's bytes for a string unique to your change** (`[System.Text.Encoding]::Unicode.GetString([System.IO.File]::ReadAllBytes($dllPath)) -match '<your new string>'`) before trusting any behavior (or non-behavior) you observe afterward. **Decode at BOTH byte alignments, or this check produces false negatives**: the `#US` heap stores UTF-16 literals at arbitrary (not necessarily even) byte offsets, so a whole-file `Unicode.GetString` garbles every literal that happens to start at an odd offset. Confirmed live — two new literals added in the same edit, in the same method, and only one of the two was found by the single-alignment decode. Also decode `$bytes[1..]` (`::Unicode.GetString($b, 1, $b.Length - 1)`) and treat a hit in *either* as a match. Search for a plain substring rather than `-match` too, since `-match` is a regex and unescaped `(`/`+` in your literal will silently change what's being searched for. This is stronger than comparing timestamps — a stale build can still get a fresh timestamp from the copy/deploy step itself, so timestamps alone don't prove the content changed. Prefer `--no-incremental` for the rebuild too, since an incremental build can silently no-op if MSBuild's own timestamp heuristics think nothing changed.
- Any temporary `File.AppendAllText`-style diagnostic logging added for a debugging session must be stripped back out once the real fix is confirmed working — it's scaffolding, not something that belongs in a merged PR (don't hardcode a dev machine's user-specific path into the add-in either). **Exception:** logging added specifically to close an observability gap identified as a real, permanent bug (not just debug scaffolding) — e.g. a silently-swallowed exception that violates PRD §01 — should stay in the merged code; use judgment (or ask) about which category a given log line falls into before stripping it.

### Any file you place directly under Revit's own install directory can silently shadow a real deploy forever

**Never copy a DLL directly into `C:\Program Files\Autodesk\Revit <version>\`** for any reason, even a one-off diagnostic (e.g. to work around a standalone test harness's own dependency-resolution needs). A same-simple-name assembly sitting there (e.g. `MCPBridge.Core.dll`) can get loaded by the .NET runtime **instead of** the real, freshly-built copy in the Addins folder — with zero indication this happened. This produced an extreme, multi-hour false lead in this project's own history: after adding a genuinely new type to `MCPBridge.Core.dll`, every single load attempt failed with `TypeLoadException: Could not load type 'X' from assembly 'MCPBridge.Core'` for every new type added, while types that existed in the assembly *before* a one-off standalone-timing-experiment DLL was dropped into Revit's install directory kept loading fine — because that ancient, accidentally-orphaned copy (not the Addins-folder one) was what actually got resolved for every subsequent Revit launch, for the rest of the session, across dozens of genuinely-correct rebuilds. **Diagnostic**: log every loaded assembly matching your project's own name prefix (`AppDomain.CurrentDomain.GetAssemblies()`, filter on name, log `.Location`) as one of the very first things a suspicious `OnStartup` failure investigation does — comparing the logged `.Location` against the Addins-folder path you expect immediately reveals a shadow copy like this. If you ever must place a file in Revit's own install directory for a genuinely one-off diagnostic (e.g. a standalone reflection-metadata harness that needs sibling native/managed DLLs on its own probing path), delete it again in the same sitting — never leave it as a "should be harmless, I'll clean it up later" artifact.

### A `TypeLoadException` from a method's own body is only catchable by its *caller*, never by that method's own try/catch

This is a real, non-obvious .NET JIT behavior worth understanding fully before writing any diagnostic probe code that instantiates types you suspect are unloadable: the JIT verifies **every type referenced anywhere in a method's body** (fields, locals, even in unreached branches) as a precondition of compiling that method at all — before a single one of its statements executes, including its own `try` block's prologue. If any referenced type can't load, the *whole method* throws immediately upon being called, and this is only catchable **from the calling method's own try/catch**, never from a try/catch written inside the poisoned method itself (that method's exception-handling regions are never entered in the first place). Two concrete consequences, both confirmed live while root-causing a genuine `TypeLoadException` in this project:
- If you inline a type-construction probe directly into a method that itself gets called from an even-more-fragile place (e.g. straight into `OnStartup`'s own try block), a poisoned reference makes **that outer method** fail to JIT as a whole — the exception surfaces at the *caller's* call site (Revit's own `AddInLoader`), completely bypassing every one of your own try/catch blocks and producing a hard, unlogged "Revit cannot run the external application" crash instead of a caught, diagnosed failure.
- If you write several independent diagnostic probes as separate helper methods but call them all from one un-wrapped sequence (`ProbeA(); ProbeB(); ProbeC();`), the first one that's poisoned aborts the *entire calling method*, silently skipping every subsequent probe — even though each one is otherwise fully independent. Each individual probe call needs its **own** try/catch at the call site, not just inside the probe's own body: `try { ProbeA(); } catch { ... } try { ProbeB(); } catch { ... }`.

Both patterns look identical to "the type just doesn't work" from the outside; the fix in both cases is the same — decompose into more, smaller, individually-wrapped methods (`[MethodImpl(MethodImplOptions.NoInlining)]` to guarantee the JIT actually treats them as separate compilation units) until the poisoned reference is isolated to one specific, minimal method body.

### Managed PackageReference dependencies aren't automatically resolved under Revit's `Assembly.LoadFrom` plugin model either

The existing `RoslynAssemblyIsolation` pattern (an `AssemblyLoadContext.Default.Resolving` handler that explicitly loads a same-directory DLL by name when default resolution can't) isn't just a Roslyn-specific workaround — it's the general fix needed for **any** NuGet package MCPBridge.Core references, because Revit's `AddInLoader` loads the add-in via `Assembly.LoadFrom`, not a `deps.json`-driven host, and that loading model does not reliably extend its own-directory probing to a referenced assembly's *own* transitive dependencies the way a normal apphost does. Confirmed live for `Microsoft.Data.Sqlite`/`SQLitePCLRaw.*`: even with every required DLL physically present in the Addins folder (verified via `Assembly.LoadFrom` succeeding on each one individually), constructing a type with a field of that dependency's type still threw `TypeLoadException` until an isolation handler analogous to `RoslynAssemblyIsolation` was added for it. **When adding any new PackageReference to `MCPBridge.Core.csproj` that isn't already covered by an existing isolation handler, add a matching one** (copy `RoslynAssemblyIsolation`'s shape, change the name-prefix filter) rather than assuming `CopyLocalLockFileAssemblies` alone is sufficient — that flag gets the *files* into the output directory, but doesn't make the CLR's default resolution actually find them from this specific loading model.

Separately (but easy to conflate with the above while debugging): **native dependencies** (a `runtimes/<rid>/native/*.dll` a package like `SQLitePCLRaw.bundle_e_sqlite3` ships) have their *own*, different gap under this same loading model — that native-library resolution needs the file physically flattened into the same directory as the managed DLLs (a dedicated MSBuild post-build `<Copy>` target, see `MCPBridge.AddIn.csproj`'s `MCPBridgeFlattenSqliteNative` target), completely independent of the managed-assembly isolation-handler fix above. A real dependency can need *both* fixes at once, for two structurally unrelated reasons — don't assume fixing one automatically covers the other.

### `prlctl exec` hangs/slowness — check for stuck processes and VM resource pressure before suspecting the code

`prlctl exec` calls that normally return in well under a second can start silently hanging for 20s–120s+, especially PowerShell invocations with a large embedded argument (e.g. a base64-encoded file payload passed via `-Command`). Before assuming this reflects something wrong with the add-in/broker being tested, check the actual cause on the **host** (Mac) side:
1. **Stuck `prlctl exec` processes accumulate silently across a long session** — every retry that times out on the harness side can leave the underlying `prlctl exec` process itself still running on the host, genuinely stuck (observed up to 6+ hours old), competing for Parallels' exec channel with every new call. Check: `ps aux | grep "prlctl exec" | grep -v grep` — if there are several, kill them (`kill -9 <pid>`) before retrying anything.
2. **The VM process itself can be under real, sustained CPU pressure** after long uptime — check `ps aux | grep prl_vm_app`. Contributing causes seen live: Windows Defender real-time scanning (`MsMpEng`) and an Autodesk background licensing/identity service (`AdskIdentityManager`) each burning tens of minutes of cumulative CPU, worse the longer the VM runs without a restart and the more disk I/O a session generates (repeated builds, file syncs).
3. **If both of the above don't resolve it, restart Parallels Desktop entirely, not just the VM** — quitting/relaunching only the VM (`prlctl restart <vm>`) doesn't reset the host-side `prl_vm_app`/`prl_client_app` processes, which is where the sustained-CPU symptom actually lives. Full restart: `osascript -e 'tell application "Parallels Desktop" to quit'` (lets the VM shut down cleanly first), wait for `prl_client_app`/`prl_vm_app` to actually exit, `open -a "Parallels Desktop"`, then `prlctl start <vm>`. **A "Parallels Desktop Update" dialog can block the relaunch** — dismiss it (`osascript` UI-scripting a click on "Remind Me Later", never "Install Update" without asking first, since a major-version upgrade is a decision for the user) before assuming the restart hung. Confirmed live: this took `prlctl exec` round-trips from multi-minute hangs back to ~0.2s.
4. **A "Technical Data Report" crash dialog may appear after instability like this** — from some Parallels helper process, not necessarily the main VM. Check the VM/app are actually still healthy first (`prlctl list <vm>`, `ps aux | grep prl_vm_app`); if so, dismiss the dialog's "Close" button without sending the report, rather than submitting diagnostic data without asking.

### Shared-folder (`\\psf\connectors`) fragility, and the local-copy fallback

The Parallels shared folder can become inaccessible to `prlctl exec`'s `NT AUTHORITY\SYSTEM` context specifically (e.g. after a VM reboot) **while the interactive user's own session retains access fine** — a session-scoping quirk in the Parallels redirector, not a real permissions problem. Confirm which is actually true before reaching for a workaround: check access from *both* contexts (`prlctl exec ... Test-Path \\psf\connectors\...` for SYSTEM, and ask the user to check via Explorer for the interactive session) rather than assuming a shared-folder failure from one context means the drive itself is down.

**The share's UNC host alias itself can change across a VM restart, not just the drive letter** — confirmed live: `\\psf\connectors` became `\\Mac\connectors` after a Parallels restart (`net use` on the VM showed the new alias mapped to a drive letter too, but drive letters are already known-unstable per the existing guidance below). Any script/tool with a **hardcoded** `\\psf\...` or `\\Mac\...` path (e.g. a default broker-exe path baked into a launcher script) will silently fail to find its target after a restart with a confusing "file not found," not an access-denied. Check the current alias with `prlctl exec <vm> cmd /c "net use"` or `dir \\Mac\` / `dir \\psf\` after any VM restart before assuming a hardcoded UNC path is still valid — and prefer resolving it fresh over hardcoding either alias where practical.

If SYSTEM-context access is genuinely broken and the interactive session still needs the files (e.g. so the launcher agent's `Start-Process` — which runs *as the interactive user* — can read them), a one-time `robocopy \\psf\connectors\... C:\dev\revit /E /XD bin obj .git` local copy is a legitimate stopgap. **But this creates exactly the drift risk described above** — treat it as temporary, prefer restoring real shared-folder access (or re-syncing explicitly per-edit, see above) over leaving a stale local copy in place indefinitely, and say so explicitly when you reach for this workaround so it doesn't get forgotten.

Also prefer **local-mode** broker discovery (`BrokerDiscoveryOptions.Local()`, `%LOCALAPPDATA%\Connectors\Revit\broker.json`) over remote/shared-drive mode for VM-local dev-loop iteration where the Mac side isn't actually involved in that test — it sidesteps the whole shared-folder dependency. Reserve remote mode for actually testing the Mac↔VM shared-drive path itself (PRD §05/§09).

### `mcp-server-win.exe -app-data-dir` — pass the full `Connectors\Revit` path, not the root

The broker writes `broker.json` **directly** into whatever directory `-app-data-dir` points at — it does not append `Connectors\Revit` itself. But `BrokerDiscoveryOptions.Local()` (the add-in side) looks for it at `%LOCALAPPDATA%\Connectors\Revit\broker.json`. Passing `-app-data-dir %LOCALAPPDATA%` (the root) writes `broker.json` one level too high, and the add-in's reconnect loop will log `broker discovery failed: (broker.json not found)` indefinitely with no other symptom. For local-mode dev-loop testing, always launch the broker with `-app-data-dir C:\Users\<user>\AppData\Local\Connectors\Revit` (create the directory first if needed) so the two sides agree on the path.

### Preflight checklist before declaring any Revit-side fix "confirmed live"

Skipping any of these produces the exact same *symptom* — "nothing changed" / "still not connecting" — regardless of which one is actually broken, which is what makes this class of bug slow to diagnose. Work through them in order rather than guessing:
1. **Source in sync?** If building from a local VM copy (not the live shared folder), re-verify it actually matches your latest edit (see above) — don't assume a prior sync is still current.
2. **Build actually recompiled?** Full rebuild (`--no-incremental`) or grep the output DLL for a string unique to your change.
3. **Deploy actually landed, unlocked?** Kill `Revit.exe`/`RevitWorker.exe`/`RevitAccelerator.exe` first; confirm via a byte-level grep of the *deployed* DLL (not just the build output) if anything is still ambiguous.
4. **Any env var involved?** If the change touches an env var the add-in reads at `OnStartup` (`MCPBRIDGE_*` etc.), the *process reading it* must be fresh — for Revit itself that just means relaunching it, but if it's launched through the launcher agent, the **agent process** must also be restarted (see "The launcher agent" above), since it holds its own stale environment snapshot independent of Revit's.
5. **Check the diagnostic log, don't infer from silence.** Read the actual log file (`connection.log`, `startup-errors.log`, or equivalent) rather than assuming success from the absence of an error — confirm the log's *own* unconditional first line (e.g. `RunConnectionLoop starting. Mode=...`) reflects what you expect before reasoning about anything logged after it.

### The VM has exactly one .NET SDK — keep it that way

The project **multi-targets two TFMs** (PRD §11), and still needs only the one .NET 10 SDK to build
both — the SDK cross-targets the older leg:
- `net10.0-windows` for Revit 2027, whose `RevitAPI.dll` requires .NET 10 (confirmed live via
  `RevitAPI.runtimeconfig.json`'s `"tfm": "net10.0"`; it will not compile under net8 — hard,
  non-suppressible CS1705).
- `net8.0-windows` for Revit 2025, whose `RevitAPI.runtimeconfig.json` declares `"tfm": "net8.0"`.

The VM has a single SDK install, `C:\dotnet10` (.NET 10 SDK, `10.0.400`), on machine `PATH` — bare
`dotnet build`/`dotnet test` resolves to it correctly. **Do not install a .NET 8 SDK to "support" the
net8 leg** — that's the exact mistake documented below, and it isn't needed.

**A multi-targeted build produces one output folder PER TFM**, so any deploy/verify step that assumed
a single `bin\Debug\net10.0-windows\` is now ambiguous: pick the folder matching the Revit version you
are deploying to (`net8.0-windows` → Addins\2025, `net10.0-windows` → Addins\2027). Deploying the
wrong leg is a silent failure of exactly the kind the byte-grep check above exists to catch. The same
applies to `dotnet test`, which now runs the suite once per TFM.

This was **not always true during Phase 1/2 development**: an early session installed a plain .NET 8
SDK to `C:\dotnet` (back when the project still targeted `net8.0-windows`, before PRD §11's correction),
and a later VM re-provisioning event reinstalled `C:\dotnet` (.NET 8) without `C:\dotnet10` ever
appearing on `PATH`. Bare `dotnet` silently resolved to the wrong SDK for a while — every build in that
stretch had actually been calling `C:\dotnet10\dotnet.exe` by its full path, masking the drift until a
bare `dotnet build` was tried and failed with `NETSDK1045: The current .NET SDK does not support
targeting .NET 10.0`. Root-caused and fixed by removing the unused `C:\dotnet` (.NET 8) entirely, so
there is now only one SDK on the VM and no ambiguity for bare `dotnet` to fall into.

**Adding a RUNTIME is fine and is not the same thing as adding an SDK — but a runtime installed to the default location is INVISIBLE to this VM's SDK.** The rule above is about SDKs; the `net8.0-windows` leg needs the .NET 8 *runtime* present to actually execute (tests targeting net8 otherwise fail with "You must install or update .NET to run this application"). Two traps, both hit live:

- **Location.** The official installer puts a runtime in `C:\Program Files\dotnet`, but this VM's SDK lives in `C:\dotnet10`, and a .NET host resolves frameworks **only from its own root** — multi-level lookup was removed in .NET 7+. So `dotnet --list-runtimes` kept showing only 10.0.11 even though 8.0.30 was correctly installed. Fix: copy the `Microsoft.NETCore.App\<ver>` and `Microsoft.WindowsDesktop.App\<ver>` folders from `C:\Program Files\dotnet\shared` into `C:\dotnet10\shared`. Both frameworks — `WindowsDesktop` matters because the TFM is `net8.0-windows`. Re-check with `dotnet --list-runtimes`; it should list both majors under the SDK's own root.
- **`RollForward` then silently undoes it.** If a project sets `RollForward=LatestMajor` (a plausible workaround when the runtime is missing), that means *roll forward to the highest available major EVEN IF the requested one is present* — so installing the runtime changes nothing, and the gap is now invisible because you believe it's fixed. Removing the property restores the default policy, which prefers the exact major.

**Installing a runtime puts a SECOND `dotnet.exe` on `PATH`; uninstalling it takes that away again but leaves hand-copied frameworks behind.** Both halves of that have now happened on this VM, and the end state is worth understanding because the machine currently contradicts itself.

- **While the runtime was installed**, `C:\Program Files\dotnet\` was on machine `PATH` and holds a `dotnet.exe` with **no SDK**. Bare `dotnet` then resolves purely by `PATH` order, and if `C:\dotnet10` is not first you get **"no .NET SDKs were found"** — a different signature from the `NETSDK1045` incident below, same underlying disease of two dotnet roots. Check with `where.exe dotnet` (expect ONE line) and `dotnet --list-sdks` (expect `10.0.400 [C:\dotnet10\sdk]`) before assuming a build failure is your code.
- **Uninstalling it** removed both the official framework folders under `C:\Program Files\dotnet\shared` and that `PATH` entry — but *not* the copies under `C:\dotnet10\shared`, since no installer ever knew about them. Net effect today: exactly one `dotnet.exe` on `PATH` (good), and `dotnet --list-runtimes` still reporting 8.0.30 (also good — the net8 test leg genuinely still executes on .NET 8, confirmed by `RuntimeTargetingTests` passing on that leg).

**So the .NET 8 frameworks here are unmanaged copies, and that is a deliberate trade with real costs.** Add/Remove Programs shows no .NET 8 runtime while `dotnet --list-runtimes` reports one, so the machine gives two different answers depending on where you look; the copies receive no servicing or security updates; and a future .NET 10 repair may not clean them. **Do not read this as "hand-copying frameworks is the pattern."** It is a workaround for a specific layout problem: with the SDK in `C:\dotnet10` and runtimes installing to `C:\Program Files\dotnet`, a *correctly* installed runtime is **structurally invisible** to that SDK, because a host resolves frameworks only from its own root and multi-level lookup was removed in .NET 7+. Reinstalling properly would not have helped on its own. The genuinely clean end state is **one root** — move the SDK to `C:\Program Files\dotnet` so SDK and runtimes are installer-managed together — and that is the fix to reach for if this ever needs touching again, rather than another copy.

**Verify by assertion, not by a green tick.** `MCPBridge.Core.Tests` now contains `RuntimeTargetingTests`, which asserts per TFM that the tests execute on the runtime they were compiled for. This exists because they once didn't: with `RollForward` in place, "274 tests passing on both TFMs" was running .NET 10's `System.Text.Json` twice — the single component whose net8/net10 divergence the multi-target exists for, since `WireEnumNameConverter` was written precisely because net8 lacks .NET 9+'s `JsonStringEnumMemberNameAttribute`. Multi-targeting a test project buys nothing at runtime unless the matching runtime is actually installed and actually selected, and only an assertion tells you which.

**If `NETSDK1045` ever comes back**, don't assume the .NET 10 SDK vanished — first check
`dotnet --list-sdks` and `[Environment]::GetEnvironmentVariable('PATH','Machine')` (via `prlctl exec`)
for a second SDK install that's shadowing `C:\dotnet10` on `PATH`. If a re-provisioning event reinstalls
a stray .NET 8/9 SDK again, remove it (kill any lingering `dotnet.exe`/`VBCSCompiler`/`MSBuild`
processes first — they hold file locks that make `Remove-Item -Recurse` fail) rather than just
reordering `PATH` around it, so this class of drift can't quietly recur a third time.

### `register`'s document list is live now — an empty list means something real

The add-in sends `register` on every successful connect AND pushes a fresh one on every document open/close/create/activate (issue #30, closed by the v1 remediation series — the document events all fire on Revit's UI thread, so the push needs no ExternalEvent). Forcing a reconnect to refresh the snapshot is obsolete; a `documents: []` that *persists* is therefore a genuine symptom, not ordinary staleness.

**Do not restart/kill any `mcp-server-mac` (or `mcp-server-win.exe`) process while your own session's `revit` MCP tool is connected — not even one you think is "someone else's."** This used to be routine (restart the broker to force a fresh reconnect, obsolete per the paragraph above) and it broke this session's own tool connection TWICE in one sitting even after the first break was diagnosed. Two distinct hazards, not one:
1. Killing the exact process your own tool's connection depends on breaks it directly (already documented elsewhere in this file).
2. **Killing ANY OTHER primary broker while your tool is connected can ALSO break it**, even if you're careful to avoid its own pid: your tool's process runs a background secondary that continuously retries lock acquisition (PRD §05's singleton lock — whichever process asks first, wins), so killing a different primary can let YOUR tool's own secondary win the race and become the new primary. Confirmed live: the client-side session then breaks too (`method "tools/call" is invalid during session initialization`), even though the underlying process stayed alive throughout. There is no way to restart *some other* broker safely while your own tool is connected — the race is inherent, not a mistake in how you did it.

If a broker restart is ever genuinely necessary for something other than the now-obsolete staleness workaround, treat it as a deliberate action that includes reconnecting your own tool afterward (`/mcp`, user-issued only — Claude Code does not auto-recover this), not a quick aside mid-task.

**`documents: []` has TWO remaining causes and they look identical from the agent side.** Work down the list in order — each check is cheap and rules its cause in or out definitively:

1. **Revit was never asked to open the document.** Check *Revit's own* records, not ours: `Select-String -Pattern '<YourDoc>' journal.NNNN.txt`, and `(Get-CimInstance Win32_Process -Filter 'ProcessId=<pid>').CommandLine`. If the path isn't on the command line, no amount of debugging the add-in or broker will explain it (see the launcher agent's atomic-drop guidance above).
2. **The document is still opening, or is blocked behind a modal dialog.** See the next paragraph — this one is genuinely nasty, and a dialog also blocks the DocumentOpened event that would have pushed the refresh.

**A modal dialog blocks Revit's idle loop, so the snapshot `ExternalEvent` never runs and `register` reports an empty list *silently*.** `DocumentSnapshotHandler` can only touch `UIApplication` from inside an `IExternalEventHandler.Execute` callback, and Revit only pumps those on its idle loop — which a modal dialog stops dead. Measured live: an event raised at 11:35:36 did not execute until 11:38:34, three minutes later, when a human finally dismissed the dialog. The add-in's own snapshot wait times out well before that and sends `register` with `documents: []` and no error anywhere. So an empty list can mean "a dialog you cannot see is holding the document hostage," and the instance will still look perfectly healthy (`status: "idle"`, auth fine, `list_instances` responsive) because the socket thread is unaffected — only the UI thread is wedged. `execute_script` is a good liveness probe for this: it also needs the idle loop, so it hangs when a dialog is up, whereas `list_instances` answers happily.

**Dialogs that fire during document *open* are outside anything PRD §07 currently intercepts.** The Failures-API preprocessor only wraps *our own* transactions, so a link-reload warning summary (`0 Errors, 80 Warnings`) raised by Revit while opening a model is not auto-answered and will block unattended automation indefinitely. Same for "File Opened By Another User". Two live examples, both hit in one session; treat this as a real gap in §07's coverage rather than environment noise.

**Revit stamps "in use" INSIDE the .rvt, so force-killing Revit taints the file — and copying it carries the stamp.** Any `Stop-Process -Force` on a Revit that has a document open leaves that document marked as open-by-another-user, and the next open shows a modal "File Opened By Another User" prompt *forever*, including for a copy made afterwards. There is no external lock file to delete. **Test against a working copy, never the pristine original**: copy the sample to somewhere writable, open the copy, and re-copy from the untouched original whenever a hard kill taints it. This keeps the kill-and-relaunch loop repeatable instead of burning one sample model per cycle.

### Never compare two Revit API objects with `ReferenceEquals`

Revit does not promise that two API calls asking for "the same" object hand back the same managed wrapper — `Document`, and by extension anything reached through one, is a thin wrapper over a native object, and each call site can mint its own. Confirmed live and instrumented: `Application.Documents`'s enumeration and `ActiveUIDocument.Document` returned **different** wrappers for a single open document (`refEquals=False`) while both resolved to the identical PRD §09 identity. That one line made `active` false for *every* document in *every* `register`/`list_instances` response the connector had ever sent, and it read exactly like a null/timing problem rather than a comparison bug.

Compare by **identity**, not reference: `DocumentIdentity.ResolveCached` produces a stable id for exactly this purpose — path-derived for saved documents, and (since the v1 remediation series) title-derived with a per-process salt for unsaved ones, so it is wrapper-independent for **every** open document. Keeping a `ReferenceEquals` arm alongside the id comparison is still fine as an exact-when-it-holds fast path, but no longer necessary for correctness. One residual caveat: a document mid-transition whose Title accessor throws falls back to a per-wrapper GUID — treat an id comparison against such a document as best-effort.

## Per-stage workflow (autonomous)

Each development stage — a roadmap phase (PRD §15) or any other discrete scope of work — runs this pipeline. Once step 1 is resolved, the rest runs without further check-ins; status lives on GitHub (the PR and its review comments), not in a running report back to the user.

1. **Questions up front, once.** Before starting implementation on a new scope of work, batch and ask whatever clarifying questions it actually needs — don't trickle them out mid-implementation. Once answered, proceed through the rest of this pipeline autonomously. The only thing that should interrupt it after this point is a genuine blocker — a decision only the user can make, not a judgment call this skill or the PRD already settles.
2. **Implement via subagent(s), TDD-first**, per the testing strategy above. The orchestrating session doesn't write implementation code directly — it delegates to a subagent (or several) so its own context stays free for spec alignment and review rather than filling up with implementation tool-call noise, and it's the one that checks the result against the PRD before moving on.
   - **MCP Server work runs in an isolated git worktree** (`isolation: "worktree"`) — it's pure Go with no dependency on the VM-mounted shared folder, so full isolation is free.
   - **MCP Bridge work runs in the main checkout, not a worktree** — the Windows VM's shared folder is bound to this repo's actual path (`\\psf\connectors\`, see PRD §05/§09), and a worktree would land somewhere the VM can't see, breaking the build. This is a real constraint, not a preference — don't isolate Bridge work into a worktree without first re-sharing the worktree's path into the VM (`prlctl set <vm> --shf-host-add <name> --path <worktree-path>`; see issue #61 for a script that should exist to do this in one step — check whether it's landed yet before doing this by hand).
   - **Every git/gh command that targets a worktree needs its own explicit `cd`/`-C` in the SAME tool call, never assumed from a previous one.** Confirmed live: the coordinating agent's shell cwd gets silently reset to the main checkout after a backgrounded command, and a later `gh pr create` run without an explicit `cd` first failed with a confusing `"No commits between main and main"` — a wrong-directory bug that read exactly like a wrong-branch one. The fix is structural, not "remember to check pwd": chain `cd <worktree-path> && git ...`/`cd <worktree-path> && gh ...` inside one Bash invocation for every command that touches a worktree, rather than issuing a bare `cd` in one tool call and a dependent command in a later one.
   - **Independent parts of a stage run in parallel.** MCP Server and MCP Bridge touch disjoint directories, so their subagents can run concurrently even though only one of them is worktree-isolated.
   - Live end-to-end validation (an actual script running against a live Revit document, per each phase's roadmap "Success" criterion) needs *both* components built and running together — that's an orchestrator-level step after the subagents return, not something to ask a single subagent to do alone.
3. **Classify the work — groundbreaking or additive — and say so in the PR description:**
   - *Groundbreaking* — introduces a new architectural pattern or subsystem that doesn't already exist in the codebase (the threading/`ExternalEvent` model, the singleton lock-or-proxy, Roslyn ALC isolation, the reflection-based discovery mechanism — most of what roadmap phases 01–03 actually are).
   - *Additive* — extends or reuses an already-established pattern (a new corpus test case, a new discovery command built on the same reflection mechanism, a new `.addin` manifest for another Revit version once the multi-target pattern already exists).
4. **Groundbreaking work only: run `/simplify` on the diff before opening the PR.** Additive work skips this step — the change surface is small enough not to need it.
5. **Open the PR** (`gh pr create`), following this repo's normal git/PR hygiene (see the standing git-safety rules: no force-push, no skipped hooks, no `--amend` on already-pushed commits).
6. **Deploy an independent code-review agent** — a fresh agent, not a fork, with no shared context from the implementation work, reading the PR diff itself rather than being told what's in it:
   - *Groundbreaking* → Opus model, reviewing for correctness and robustness.
   - *Additive* → default model (Sonnet) is sufficient.
   - The agent posts its findings to the PR on GitHub (a review or summary comment) so they're visible without being relayed manually, and reports back with a short summary of what it found.
7. **Merging is not automatic.** This pipeline creates and reviews PRs autonomously — it does not merge them. Merge stays a human decision unless explicitly told otherwise later.

## Milestone retrospectives

**After completing any major milestone — a PR series, a roadmap phase, a multi-PR feature — run a short retrospective before starting the next one.** The goal is a smooth, fast, agile loop, and the loop only improves if friction gets converted into fixes while it's fresh. Ask three questions, spend no more than a few minutes each, and act on the answers immediately (a SKILL.md rule, a dev-tooling change, or a filed issue — never just a mental note):

1. **What broke or hung during the work itself** — not the product, the *process*? (A script that wedged, a command retried three times, a tool misuse, verification that lied.)
2. **Where did wall-clock go that wasn't thinking or building?** (Round trips, re-runs, waiting on something that could be parallel or cached.)
3. **What did a reviewer or a test catch that the process should have caught earlier — or cheaper?**

Rules distilled from the v1-remediation-series retrospective (the first instance of this practice), each of which cost real time once:

- **Shell discipline in agent sessions**: use absolute paths in every command (the session shell's cwd drifts and `cd` failures silently skip `&&` chains); never put destructive commands (`git push --delete`, `rm`) after `;` in a chain whose earlier `&&` parts can fail — the `;` parts run anyway (this deleted an open PR's remote branch mid-series, closing the PR); in background pipelines, `grep` needs `--line-buffered` or the output file stays empty until exit.
- **Git safety around uncommitted work**: commit (or stash) before any mutation-test dance — a reflexive `git checkout <file>` to "restore" restores the *branch's* version and destroys uncommitted fixes. Delete a PR's branch only after `gh pr view` confirms MERGED.
- **VM round-trip economy**: tier-1 C# verification costs ~60s×2 TFMs per run via `prlctl exec` — iterate with `--filter <TestClass>` (or one `-f <tfm>`) and run the full both-TFM suite once at the end, not per edit. Closing issue #39 (C# CI via the Nice3point packages) is the structural fix; until then the VM is the only C# checker, so batch edits before verifying.
- **RevitAdapter static-initializer trap**: a static field on a type whose *other* statics reference Revit types (e.g. a `ConditionalWeakTable<Document,...>`) makes the whole type initializer load RevitAPI.dll — which a tier-1 test host cannot do. Members meant to be tier-1-reachable must not share a type initializer with Revit-typed statics; put new static state in a nested holder type (see `DocumentIdentity.UnsavedIdentitySalt`).
- **Run the budget/consistency tests nearest the file you just edited, immediately**: `internal/mcpserver`'s skill-file token-budget test is sub-second and local — editing the embedded skill.md and discovering the overage two steps later (or in a full-suite run) wastes a cycle.
- **Anything a dev script backgrounds must be detached from the script's own stdio** (`</dev/null >>log 2>&1`, backgrounded from the outer shell) or every pipeline consumer of the script inherits the daemon's lifetime — the redeploy-and-verify pipe hang. Corollary for driving long scripts from tooling: file-backed background output, not an EOF-waiting pipe.
- **Exclusions outlive their reasons**: when a change upgrades a previously-unreliable value into a reliable one (per-wrapper tmp- GUIDs becoming stable title-derived ids), search for every site that special-cases the old unreliability — a guard written for the old world silently becomes the bug in the new one (`ActiveDocumentPredicate`'s tmp- exclusion resurrected the always-inactive bug for unsaved documents the moment the ids became comparable; caught by PR #50's independent review, not by the change's author).
- **Never let the only copy of a verification result pass through a lossy filter** — three times in one session a `tail`/`grep` chain destroyed exactly the evidence needed (a PASS invisible behind a hung pipe, a FAIL's test name cut by `tail -3`, failure names eaten by a match-nothing second grep whose exit code then masqueraded as the suite's). Tee the COMPLETE result-line stream to a file, filter the file afterwards; a filter's empty output must never be the only record.
- **Harness iteration economy** (test-quality-pass retro): iterate a failing tier-2 case with `go test -tags harness -run <Case>`, full suite once at the end — the same rule as tier-1's `--filter`, for the same reason (several ~8-minute full runs were spent where 1-minute filtered ones would do).
- **Forked subagents cannot spawn their own reviewers** — when implementation is delegated to a fork, the coordinator spawns the true independent review; a fork's self-review (however fresh-eyed) missed the dominant-case hole in PR #48 that the independent pass then caught with a demonstration test.
- **Parallel-PR mechanics that worked, kept as defaults**: implementation/review agents work from `gh pr diff` + `git show origin/<branch>:<path>` or their own git worktree, never by switching the main worktree's branch (the VM shared folder is bound to the main checkout, so live verification owns it); two PRs that both append to this file's changelog will conflict — resolve keep-both, chronological.

- `redeploy-and-verify.sh` was unsafe to pipe, and the shape of the bug generalizes: `( cd ... && nohup <broker> & disown )` left the parenthesized subshell alive for the broker's whole lifetime, still holding the script's inherited stdout/stderr — so `redeploy-and-verify.sh | anything` hung forever at the end (the script exited; the consumer never saw EOF), and the `disown` was disowning in the wrong (inner) shell, which is where the stray `Terminated: 15` lines on each reaction cycle came from. Found because a live-verify run was piped through `tail -30` for the first time; the run itself had PASSed minutes earlier, invisibly. Fixed form: `( cd ... && exec nohup <wrapper> </dev/null >>log 2>&1 ) & disown` — `exec` removes the lingering middleman, the explicit redirects detach every inherited fd, and the backgrounding+disown happen in the outer shell whose job table matters. Two transferable rules: **anything a script backgrounds must be detached from the script's own stdout/stderr, or every pipeline consumer of the script inherits the daemon's lifetime**; and when driving a long-running script from tooling, prefer `run_in_background` (file-backed output, no EOF dependency) over piping through an EOF-waiting consumer — the pipe turns any fd leak anywhere in the script into a hang at the harness level.
