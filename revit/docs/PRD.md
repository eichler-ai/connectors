# Revit Connector

**Product & Technical Design — Draft**

Two components — the Revit MCP Bridge, a Revit add-in that executes dynamic C# against live documents, and the Revit MCP Server, which speaks MCP to Claude and other agents over a local, structured protocol — starting with Revit 2027.

- **Scope:** v1 = Revit 2027 only
- **Trust model:** fully trusted, unsandboxed
- **Transport:** TCP JSON-RPC 2.0, NDJSON framing
- **MCP Server:** Go, single-binary distribution
- **Status:** phases 1–3 shipped (core loop, dialog suppression + multi-instance, API discovery + file exchange), phase 6 partial (Revit 2025 support), plus the Aug 2026 v1 remediation series (per-document routing, live document snapshots, execution audit trail, and the defect/hardening sweep from a four-partition integrated review) — see §15 for per-phase status

## 01. Summary & goals

Every existing open-source Revit-MCP project (surveyed below) wraps the Revit API in a fixed catalog of 20–170 pre-built tools — `create_wall`, `export_ifc`, and so on. This connector inverts that: the primary surface is `execute_script`, which compiles and runs arbitrary C# against the live document, with three companion commands — `list_functions`, `search_functions`, `describe_function` — that let the agent read Revit's own API documentation on demand instead of being limited to whatever the plugin author thought to expose.

> **Guiding principle — fully autonomous project-lifecycle control, done correctly, efficiently, and safely.** The connector's north star is letting an agent drive Revit through an entire project's lifecycle (design, modeling, annotation, documentation, export) without a human at the keyboard for routine work. That autonomy has to hold on all three axes at once, not trade one for the others: **correctly** — following the same conventions and standards a competent practitioner would (naming, project/document standards, valid modeling practice — not just "compiles and doesn't crash"); **efficiently** — mindful of both token budget and wall-clock time, not brute-forcing discovery or re-deriving context on every call; and **safely** — protected against both agent mistakes and human missteps, since full autonomy means no one is double-checking each action before it runs. This is why `execute_script`'s design includes things that look like friction at first glance — `ScriptApiDenylist` (§14), confirmation-gating for document-lifecycle actions, the observability-over-silence principle below. None of it exists to slow the agent down for its own sake; "fully autonomous" only holds up if safety is actually designed in, not assumed. See the `revit-connector-development` skill's "Script API surface" section for the concrete test this principle implies for anything added to or removed from the denylist.

Goals for v1:

- Run agent-authored C# against an open Revit 2027 document without crashing the host or corrupting the model.
- Suppress modal dialogs raised by API calls so a script's thread never hangs waiting on a click that will never come.
- Let one MCP connection reach multiple simultaneous Revit instances, addressed explicitly by instance and document.
- Give the agent a self-serve way to learn the API surface instead of hard-coding tool wrappers per capability.
- Keep generated files (exports, logs, script history) in one predictable, per-document location on disk.

> **Design principle — observability over silence.** Anywhere the add-in automatically resolves something on the agent's behalf — a suppressed dialog, an auto-dismissed transaction warning, a cancelled execution — that resolution is reported back in the result, never handled invisibly. The agent needs to detect when something was papered over and navigate around it, not just receive a clean-looking success that hides what actually happened. This shapes §07 (non-framework dialogs), §07 (transaction failures), and §06 (cancellation) identically, and should hold for any future automatic-resolution feature, not just the ones specified today.

### Observability & error reporting standard

The principle above only holds if every subsystem reports things the same way. One shared diagnostic-record shape, reused in three places — the `notices` array on any successful result, the `data` field of any JSON-RPC `error`, and every NDJSON log record in §09's `logs/` directory:

```json
{
  "severity": "debug" | "info" | "warning" | "error",
  "code": "<stable machine-readable identifier>",
  "source": "<component tag — matches the repo's module layout>",
  "message": "<specific, concrete — see requirements below>",
  "detail": { "...code-specific structured fields...": "..." },
  "remedy": ["<suggested next step>", "..."]
}
```

- **Which channel carries what.** Auto-resolved warnings (the Failures API in §07, and anything later) populate `notices[]` on the successful result — severity there is `warning`/`info`, never `error`. An error-severity condition rolls the transaction back and surfaces through the JSON-RPC `error` path instead, not `notices` — the two channels don't overlap. A third field, `mutations` (#146 Phase 2), is neither: it is a *report*, not a diagnostic — the run's net created/modified/deleted effect across every document it changed, present only on a success that changed something. Notices are for things resolved on the script's behalf; what the script itself did is a result. The same run's entry in Revit's **Undo history** is named for the human (#146 Phase 2b): an agent-supplied `label` → `MCP: <label>` (sanitised to one line, capped), else a name derived from *that document's* net report (`MCP: 12 Walls created`), else `MCP Bridge Script`. The rename is cosmetic by contract — it never fails a commit — but a refused rename is reported (`undo-label-not-applied`), never swallowed.
- **`code` is kebab-case, one convention connector-wide** *(unified in the v1 remediation series; before it, broker-minted codes were snake_case and add-in-minted ones kebab-case — two conventions nobody chose)*. Codes are stable machine-readable identifiers agents match on, so the style is part of the wire contract: new codes are kebab-case everywhere, and the pre-unification snake_case spellings are gone (renamed while nothing external depended on them — after open-sourcing, such a rename is a breaking change). MCP tool names (`execute_script`) and JSON field names (`execution_id`) are snake_case per MCP convention and are not diagnostic codes.
- **`source` is how "find the relevant code" gets satisfied without going stale.** Values match the module names already in the repo layout directly — `mcp-bridge.core.execution`, `mcp-bridge.core.dialogs`, `mcp-server.internal.registry`, and so on — rather than a separately-invented taxonomy or a file:line reference that breaks the moment code moves.
- **`message` is a hard rule, not a suggestion.** Must include the concrete identifiers involved (`execution_id`/`instance_id`/`document_id`, whichever apply) and the actual underlying condition — never a generic wrapper like "An error occurred" or "Execution failed" that discards what a wrapped .NET/Go exception actually said. Wrap, don't replace: the original exception's own message/type is part of `message` or `detail`, never swallowed.
- **`remedy` is expected, not decorative.** "Restart Revit to recover this instance," "call `list_instances` to confirm the new `document_id`, then retry," "dismiss the listed window manually, then reissue `execute_script`." Omit it only when there's genuinely nothing actionable to suggest, not by default.

**Two channels, not one, for the same record.** MCP's `tools/call` contract expects a failed tool call to surface as a normal result with `IsError: true` and readable content — not a JSON-RPC protocol-level error — so the calling agent sees and can react to it as tool output. That's a different shape than the broker↔add-in wire protocol, which is entirely our own design and free to use raw JSON-RPC `error.data` as specified above. Resolution: the shared diagnostic record is the same in both places, just carried differently — literally in `error.data` on the internal wire protocol, and in `CallToolResult`'s structured/text output with `IsError` set at the MCP tool layer. Don't conflate the two when implementing either side.

**`execution_id` is broker-minted.** The broker generates it before forwarding a script to the owning add-in, so it can route `poll_execution`/`cancel_execution` to the right instance without a second round trip; the add-in echoes the same ID back in every response rather than generating its own.

## 02. Non-goals for v1

- **Not multi-version yet.** Build and validate against 2027 only; the project is structured so 2025/2026 support is an additive multi-target step later, not a rewrite.
- **Not a general sandbox.** `execute_script` gets full Revit API access with no broad permission gate or read/write distinction — this is a local, user-initiated dev tool, not a multi-tenant service. The one exception is `ScriptApiDenylist` (§14): a narrow, principled block on the small set of operations that escape the ambient transaction's rollback guarantee — safety-by-design for a fully autonomous agent (§01), not a permission system. Reflection can still route around it, and that's accepted, not a gap to close.
- **Not marketplace-listed at launch.** Signing and Autodesk Marketplace submission are a later milestone; v1 distributes as a signed installer via direct download.
- **Not a fixed-tool-catalog product.** We deliberately don't compete with the existing projects' breadth of pre-built commands — `execute_script` plus API discovery is the bet.

## 03. Competitive landscape

Six-plus open-source "Revit MCP" projects exist as of mid-2026; all are young (single-digit to low-hundreds stars) and none has become a reference standard. The pattern across all of them: a fixed tool catalog is the default, arbitrary script execution is at best a secondary escape hatch, and none expose progressive API discovery.

| Project | Tool model | Dialog handling | API discovery | Multi-instance |
|---|---|---|---|---|
| mcp-servers-for-revit/revit-mcp *(archived)* | 24 fixed tools + `send_code_to_revit` | test dialog only | none | unaddressed |
| IbrahimFahdah/revit-claude-mcp | 46 fixed tools, package-extensible | undocumented | none | unaddressed |
| LuDattilo/RevitCortex | 173 fixed tools + namespace-sandboxed `send_code_to_revit` | shows native confirms, doesn't suppress | capability hiding only, not help text | single bridge implied |
| UV-Tech/revit-claude-mcp | 40 fixed tools, no script exec | disables its own dialog, not general | health-check only | single fixed port |
| Demolinator/revit-mcp-plugin | 48 fixed tools (pyRevit-based) | — | — | — |
| Autodesk Revit Public MCP Server *(official, Tech Preview, 2027)* | fixed query/report/snapshot tools; sources conflict on whether bulk parameter-value edits are included — no version creates or deletes elements | undocumented | none | undocumented |
| AUTOM8LABS MCP Connector *(3rd-party, live on marketplace.autodesk.com)* | 37 fixed tools, read-only free tier | undocumented | none | undocumented |
| **This connector** | **execute_script as primary interface** | **DialogBoxShowing suppression, general** | **list/search/describe against RevitAPI.xml** | **explicit instance + document targeting** |

Two structural facts validate the differentiation: threading via `ExternalEvent` is already standard practice across these projects, so nothing novel is needed there — but modal-dialog suppression, real API discovery, and multi-instance addressing are gaps every surveyed project either skips or fakes.

One newer fact cuts the other way: as of mid-2026, "AI-agent MCP connector for Revit" is a real, approved marketplace category — Autodesk shipped its own official MCP server and a third-party connector is already live — but **every entrant, including Autodesk's own, deliberately avoids arbitrary code execution** in favor of fixed tool catalogs, and Autodesk's own server's write capability (if any) tops out at parameter-value edits — sources conflict on whether even that shipped, and neither confirms element creation or deletion. That consistency across both open-source and officially-sanctioned entrants is the strongest signal available on the open marketplace-review question in §14.

## 04. Architecture

Three tiers, matching the pattern used by comparable GUI-app bridges (Blender MCP, Unity MCP): the **Revit MCP Bridge** (the add-in) never speaks MCP — it's a plain TCP JSON-RPC executor. A separate process, the **Revit MCP Server** — internally called "the broker" throughout this doc — run wherever Claude runs, is the only thing that speaks MCP over stdio, and it fans out to however many Revit instances are alive.

```
Claude / Claude Code  <--stdio-->  Revit MCP Server (broker)  <--TCP/NDJSON-->  MCP Bridge (Revit instance A)
                                    runs on Claude's host                       dials out on startup
                                    registered to Claude as "revit"
                                    owns instances.json registry     <--TCP/NDJSON-->  MCP Bridge (Revit instance B)
                                                                                        dials out on startup
```

MCP tool calls exposed to the agent: `execute_script`, `poll_execution`, `cancel_execution`, `list_functions`, `search_functions`, `describe_function`, `list_instances`.

### Naming & terminology

This connector is the first of what's expected to be several in a shared connectors repo, so naming is deliberately layered rather than ad hoc:

| Context | Add-in | Agent-facing server |
|---|---|---|
| Inside the Revit connector's own directory/docs | MCP Bridge | MCP Server |
| Outside that context — repo root, cross-connector docs, anywhere "MCP Server" alone would be ambiguous | Revit MCP Bridge | Revit MCP Server |
| Inside Revit's own UI | MCP Bridge (no "Revit" prefix — redundant when you're already inside Revit) | n/a |
| Inside Claude's MCP client config | n/a | `"revit"` — the literal server registration key/slug |

"The broker" is the internal engineering shorthand used throughout this doc for the Revit MCP Server — the same single process, not a sub-component inside it; "the add-in" is the equivalent shorthand for the Revit MCP Bridge. There's no umbrella product name distinct from the connector itself — this doc refers to the whole system as "this connector" or "the Revit connector," never as "MCP Bridge" alone, to keep that term unambiguous for the add-in specifically.

> **Repo-wide convention, documented here first.** The Bridge/Server split — an in-process add-in plus a separate agent-facing MCP server — is the general pattern for any future connector to an app with the same constraints (single-threaded UI API, needs an in-process executor), not a Revit-specific naming choice. Captured in the repo root's `CONVENTIONS.md`.

The add-in stays intentionally thin: a TCP client, a Roslyn script runner, a `DialogBoxShowing` handler, and live reflection over `RevitAPI.dll`/`RevitAPI.xml` serving §08's discovery commands directly, on the connection thread rather than through `ExternalEvent`. Every piece of MCP-protocol churn — schema versions, new transport features — lives in the broker, which can be updated without resigning or redistributing the signed Revit DLL. One small piece of user-facing UI sits outside this list deliberately: a single "MCP Bridge" ribbon panel with a "Status" button (Add-Ins tab), showing live connection state and build identity in a non-modal window — a diagnostic convenience the add-in's own live-wiring development made clear was worth having, not a step toward a broader in-Revit UI surface.

### MCP Server implementation language — Go

The broker ships as a self-contained binary, not an npm-installed Node process — the target user shouldn't need a JS toolchain just to run a local bridge. That distribution requirement, not raw SDK maturity, is what decides the language: both Go (`modelcontextprotocol/go-sdk`, built with Google, ~5k stars) and Rust (`rmcp`, ~3.8k stars, actively maintained) have solid official MCP SDKs with first-class stdio transport support. Go wins on the deployment story specifically — a single build-flag cross-compiles a self-contained binary for any target with no extra toolchain install and no runtime DLL dependency; Rust's equivalent cross-compile needs an added target and linker set up first. The broker's own responsibilities (stdio MCP server, TCP listener/client for the add-in protocol, JSON-RPC/NDJSON framing, the singleton lock-or-proxy logic in §05) are all straightforward in Go's standard library, so nothing about the broker's actual workload favors Rust enough to offset the simpler cross-compile.

The primary build target is `GOOS=windows GOARCH=amd64` — local mode (§05) always runs the broker on the same Windows machine as Revit. A `GOOS=darwin` build of the same codebase exists specifically to run the broker on the Mac side of a remote-mode setup (this project's own dev environment); it isn't a second product, just a second build target of one binary.

## 05. Connection & multiplexing model

**Each Revit instance dials out to the broker** on a well-known local port at startup, rather than the broker dialing into Revit. This is the opposite of the obvious design, and it's deliberate:

- **One address, many instances.** The broker owns a single listening port; every Revit instance is just another inbound connection, tagged with an instance ID and its list of open documents. The agent addresses `{instance_id, document_id}` in every call — this is the "single multiplexed port with instance IDs" model, chosen over one-port-per-instance because ports-per-instance push discovery and routing work onto the agent for no real benefit.
- **Outbound-only avoids needing inbound port-forwarding.** Whatever machine the broker ends up bound on, the add-in only ever needs to dial *out* — it never needs a port opened for inbound connections into Revit's machine. That much holds in every topology. It does *not*, on its own, make a Mac-hosted broker reachable from a VM: a loopback-bound broker answers nothing outside its own machine regardless of which direction the dial runs. Reachability is the topology question below, not a side effect of dialing outward.

> **Framing.** JSON-RPC 2.0 defines no message boundary. We use newline-delimited JSON (one object per line) rather than LSP-style `Content-Length` headers — simpler to implement on both the C# `TcpClient` side and the Go broker side, and safe because valid JSON never contains a literal unescaped newline.

Instance registration: on connect, each add-in sends a `register` notification with instance ID (GUID, generated once per Revit process at `OnStartup` — stable for that process's lifetime, independent of any particular broker connection), PID, Revit version, and the list of currently open documents. **That list is now live, not a one-shot snapshot** (issue #30, closed by the v1 remediation series): the add-in subscribes `DocumentOpened`/`DocumentClosed`/`DocumentCreated`/`ViewActivated` and pushes a fresh `register` over the live connection on each — the same message, the same broker-side replace semantics, built by the same snapshot code as the connect-time one, from the UI thread the events already fire on. (An earlier version of this paragraph documented the opposite — a connect-time-only snapshot whose staleness the dev tooling worked around with forced broker restarts; that scaffolding is deleted.) A briefly-empty `documents[]` right after a launch still just means the document hasn't finished opening. The broker maintains this as live state and also mirrors it to a local `instances.json` so the broker itself is restartable without losing visibility (Revit instances just reconnect).

### Local vs. remote topology

Reverse-dial, loopback-only binding, and file-based `broker.json` discovery all silently assumed broker and Revit share a machine and a filesystem. That's true for the real target deployment but false for this project's own Mac+Parallels dev setup, so topology is now an explicit choice instead of one flow with a hidden assumption baked in:

| | Local mode (default) | Remote mode (opt-in) |
|---|---|---|
| When | Broker and Revit on the same OS instance — the real target deployment | Broker and Revit on different machines — e.g. broker on the Mac, Revit in the Parallels VM |
| Broker bind | `127.0.0.1` only | A specific configured non-loopback interface (e.g. the Parallels shared-network host adapter address) — never `0.0.0.0` |
| Add-in discovery | Reads local `broker.json` — valid since it shares a filesystem with the broker | Same file-based discovery, pointed at the shared drive's agreed root instead of local app-data (§09 already needs this drive for file exchange, so discovery reuses it rather than inventing a second mechanism). A shared drive is REQUIRED in remote mode: the auth token rides in `broker.json` (§10), so the once-planned `broker_host:port` fallback could never authenticate — it shipped as dead configuration and was removed (v1 remediation series); a no-shared-drive remote topology needs a real auth story first |
| Auth | Same-user-local trust, per §10 | The broker-minted token in `broker.json` (§10), which the shared drive carries — remote-mode security is bounded by access to that drive, a named limitation in §10. (An earlier draft of this row said "not yet specified"; the token has carried remote auth since Phase 1, and §14's finding 5 records it as resolved) |

The reconnect loop, singleton lock-or-proxy, and instance registry below behave identically in both modes — only the bind address and discovery mechanism change.

### Startup ordering & reconnection

The broker is only started on demand — spawned via stdio whenever an MCP client actually needs it — so it may come up before, after, or interleaved with any number of Revit sessions, and a Revit instance may run its entire session without a broker ever attaching. One mechanism covers all of these instead of special-casing each:

- **Add-in: a single retry loop, not an event-driven connect.** At `OnStartup`, and again immediately after any dropped connection for any reason (broker not yet running, broker crashed, broker restarted), the add-in retries dialing the broker on a backoff (1s, rising to a ~15–30s cap), indefinitely, with no dialog and negligible idle cost. First connect, reconnect-after-restart, and "Revit open with no broker ever showing up" are all this same loop — not three behaviors.
- **Broker: listens before anything else.** Binds and starts accepting TCP connections as the first action on launch, before completing its own MCP/stdio handshake, so an add-in already mid-backoff connects on its very next attempt. In **local mode** it writes `broker.json` (port, PID, start time, and a fresh auth token — see §10) to a platform-appropriate app-data directory as the discoverable source of truth for "where am I," and the add-in reads it on each retry rather than assuming a fixed port. In **remote mode** the same file is written to the shared drive's agreed root (§09) instead — same retry loop, same file, different location (and no host:port fallback; see the topology table above).
- **Recovering state, not just the socket.** On every successful connect — first time or reconnect — the add-in re-sends `register` with its stable `instance_id` and current documents, and replays a small ring buffer of recent execution results (last N / ~10 minutes) that it keeps independently of the socket, so `poll_execution` against an `execution_id` still resolves after a broker restart, as long as Revit itself didn't also restart. If an `execution_id` genuinely can't be found (Revit/the add-in restarted), `poll_execution` returns an explicit "unknown execution_id" error rather than hanging.
- **Heartbeat, not just connection state.** A live TCP connection doesn't mean the add-in is actually responsive — Revit can wedge without the socket dropping. The add-in sends a lightweight periodic ping over the existing connection (no new message type, just piggybacked on the same NDJSON stream); the broker marks an instance `unresponsive` — distinct from `unrecoverable`, which specifically means "cancellation's grace period lapsed" (§06) — after a few missed intervals, and prunes it from the registry after a longer timeout with no ping at all. This is what actually backs `list_instances`' `status` field, rather than it being inferred solely from connection state.

### Broker singleton & port contention

Because the broker is stdio-spawned per MCP client, two concurrent Claude sessions each configured against this server would naively spawn two broker processes racing for the same TCP port. Resolved with a lock-or-proxy pattern, deliberately reusing the same "acquire or fall back" shape as the reconnect loop above rather than introducing separate promotion logic:

- On launch, every broker process attempts to take an exclusive OS-level lock (`LockFileEx`/equivalent) on a single lock file. Whichever process gets it becomes **primary**: binds the TCP port, generates a fresh auth token and writes it into `broker.json` alongside the port/PID, and owns all Revit connections and routing.
- A process that doesn't get the lock becomes **secondary**: it doesn't bind a port at all. Instead it reads the same `broker.json` the primary just wrote — which is how it discovered there already was a primary in the first place — and connects to the primary's TCP port as a client, presenting that same token, tagged at registration as an agent-client rather than a Revit instance, and simply forwards its own stdio MCP calls through that connection for the primary to route. From the agent's point of view behavior is identical regardless of which broker process it happens to be talking to.
- If the primary exits, its lock releases and its `broker.json` goes stale. A secondary that notices its upstream connection drop re-runs the same lock-acquisition step — it may become the new primary, or find another secondary got there first and keep proxying. Revit instances discover the new primary the normal way, through their own reconnect loop reading `broker.json`.

### Instance discovery — `list_instances`

Before an agent can target `{instance_id, document_id}`, it needs to see what's actually live. `list_instances` returns the broker's current registry directly — no round-trip into Revit required, since every field is already tracked from `register`/heartbeat traffic:

| Field | Scope | Notes |
|---|---|---|
| `instance_id` | instance | Stable for the life of the Revit process (§05). |
| `revit_version`, `pid` | instance | e.g. `"2027"` — relevant once multi-version ships (§11). |
| `connected_since` | instance | Timestamp of the current connection, not the Revit process's launch time — resets across a reconnect. |
| `status` | instance | `idle` / `pending` / `busy` / `unrecoverable` / `unresponsive` — the first four mirror the state from `execute_script`/`poll_execution`/`cancel_execution` (§06); `unresponsive` comes from the heartbeat above rather than execution state, and covers the case a script never even reported — Revit wedged without the socket dropping. |
| `documents[]` | per document | `document_id`, title, path (or "unsaved"), workshared flag, and whether it's the instance's active/foreground document. |

Each entry's `document_id` follows the identity scheme in §09 — a `doc-` hash for anything with a stable path (preferring the central model path over a workshared local copy's path), or a `tmp-` session GUID for anything unsaved or detached-and-not-yet-saved, so `list_instances` is legible and stable enough for an agent to pick the same target twice in a row.

## 06. Threading & script execution

The Revit API is single-threaded and callable only from the main UI thread. The TCP socket and Roslyn compilation can happen off-thread, but every actual API touch cannot. Standard pattern, used across the ecosystem (and packaged as `Revit.Async`):

1. TCP thread receives an `execute_script` request, decodes it, and hands the script text to an `IExternalEventHandler`.
2. `ExternalEvent.Raise()` wakes Revit's idle loop; `Execute(UIApplication)` runs on the correct thread.
3. Inside `Execute`, the script is compiled/run via Roslyn scripting, with a globals object exposing `Document`, `UIApplication`, and `UIDocument` into script scope. Isolation and memory lifecycle are covered separately below — the naive "cache every compiled `Script<T>` for the session" approach doesn't hold up under real agent usage.
4. The call runs inside a connector-owned `TransactionGroup` per document (the rollback boundary); the script's `Connector.WithTransaction` blocks open the transactions inside it, so failed scripts roll back cleanly; stdout is captured into the result's `output`, the script's own returned value is formatted into the separate `return_value` field (they are separate because Revit writes to the process console during a script, so `output` is not the script's alone — issue #117), and any exception populates the JSON-RPC `error` using the shared diagnostic-record shape (§01) — never a bare wrapper message.
5. The result is signaled back to the waiting TCP thread via a blocking handoff (e.g. `TaskCompletionSource`), never returned directly from `Execute`.

> **Risk.** A script that spins forever, or an API call that genuinely blocks on I/O, occupies Revit's UI thread until it returns — there is no preemption.

### Transaction state — `group-always`, transaction-on-write

*(Revised by issue #146, Phase 3, September 2026. The model this section originally argued for — `always-open` plus `settle-on-request` — shipped in #24/#132 and was then superseded; the history is kept below because the reasoning that chose the successor is the reasoning that chose it.)*

**The model is `group-always`, transaction-on-write.** For every document a run touches, the connector opens a `TransactionGroup` before the script runs — and **no** `Transaction`. The document is readable and *not modifiable*. The script writes inside `Connector.WithTransaction(doc, body)`; the connector opens a transaction in the group for the block (attaching its Failures-API preprocessor, §07), commits it at block end, and returns the body's value. At run end an **empty** group (nothing committed) is rolled back — a read-only run leaves no undo entry — and a non-empty one is `Assimilate`d under a per-document `UndoLabel` (the caller's `label`, else a derived "MCP: 12 Walls created"), so a whole run is one entry in Revit's Undo menu. A script that throws rolls back every document's group, created-first/adopted/ambient-last as before. A block on a document the run has not touched *adopts* it with a group of its own; that is how the created documents of one call are written in the next, and it replaced `Connector.OpenForWriting`.

Its cost is that every write is now inside a block, and `Level.Create(Document, 10.0)` at top level — the most-taught line in `skill.md` for two releases — throws `script-write-outside-transaction` with a remedy naming the block. That cost was paid deliberately, for what it buys:

**The enabling fact, verified live against Revit 2025 and 2027, is that a group and a transaction do different jobs.** A `TransactionGroup` is the *rollback boundary*; a `Transaction` is the *modifiable flag*. With a group open and no transaction, `Document.IsModifiable` is `false` — and `TransactionGroup.RollBack()` still discards transactions that already committed inside it, so all-or-nothing survives an inner commit. That state satisfies every API the previous default refused: `Document.LoadFamily`, `UIDocument.RequestViewChange`/`ActiveView`, `UIApplication.OpenAndActivateDocument`, `Document.Export`, and every `EditScope` — stairs above all (#113–#118 were one root cause wearing five faces). Under `group-always` those calls simply work *between* blocks, with the agent knowing nothing, which is what `always-open` + `Connector.WithoutTransaction` could never claim. `Close`/`SaveAs` remain blocked by the group itself and still go through `Connector.Settle`.

**Why group-always rather than a lazily opened group.** The stronger-looking variant opens nothing until the first block. It was rejected because the group is what makes a run's writes *one* undo entry and one rollback unit, and it must exist before the first block commits into it — which it would under either variant. What lazy-open would save is the group on a read-only run, and an empty group rolled back is free (no undo entry, no regeneration, verified live). What it would cost is that a document adopted by a block mid-run and a document routed from the start would be in different states before their first write, and `ManagedDocumentTransactions` would carry two lifecycles for one guarantee. Uniform cost, uniform state.

**Why transaction-on-write rather than the previous transaction-for-the-run.** The transaction was the thing every refused API objected to, and it was open the whole run for no benefit a block does not also give: the script's writes were never visible to the person until commit either way. What was lost is `Failures`-API capture for writes outside any block — and there are none now, since such a write throws. What was gained beyond the API list: an empty group leaves **no undo entry** (a read-only run under `always-open` left one, since an empty transaction committed into the group still assimilated), a block that throws rolls back only its own slice and the document stays usable (`try { WithTransaction } catch` is catch-and-continue), and `undo`/`redo` (Phase 2c) act on exactly one run.

| Scope | Does | Reaches |
|---|---|---|
| `Connector.WithTransaction(doc, body)` | opens a transaction in the document's group (adopting the document with a group if this run has none), closes it at block end, returns the body's value | every write; the write inside an edit scope |
| *(no block)* | the resting state: group open, document not modifiable | `LoadFamily`, `RequestViewChange`, activation, `Export`, `EditScope.Start`/`Commit` |
| `Connector.Settle(doc, keep:)` | settles the group — assimilate to keep, roll back to discard | `Close`/`Save`/`SaveAs`/`SynchronizeWithCentral` **in-run** |

`Connector.WithoutTransaction` and `Connector.OpenForWriting` are removed, not deprecated: the first described a state that is now the default, the second a step a block now takes itself. `ScriptApiDenylist` check 1's syntactic rule is unchanged — the script still never constructs a Revit transaction — and its refusal message now names the block. A native `SubTransaction` is permitted as a savepoint inside a block, held in a `using` (Phase 1).

**The governing constraint is that the script declares intent and the connector never infers it**, and that is a finding rather than a preference. The first design had the connector notice a lifecycle call and settle on the script's behalf (`settle-on-lifecycle`). It has no mechanism: the script calls `doc.Save()`/`doc.Close()` on the real `Autodesk.Revit.DB.Document`, and `ScriptApiDenylist` is a compile-time walk that detects and gates but cannot intercept. The obvious hook does not exist either — verified live, **neither `DocumentSavingAs` nor `DocumentClosing` fires** when a group is open, because Revit's transaction-phase check precedes event dispatch. A design that reacts to a lifecycle operation is therefore unbuildable, and one where the script states the direction needs no interception at all.

**What `settle-on-request` did not change** (written under `always-open`; still true under `group-always`): `ScriptApiDenylist`, in either check; §14's confirmation gate; and `ManagedDocumentTransactions`' commit ordering — created-first/adopted/ambient-last still holds **for every document that was never settled**, because inner commits assimilate into a still-open group and nothing lands irreversibly before `CommitAll`. A settled document is the exception and must be read as one: `Settle(keep: true)` lands irreversibly *before* `CommitAll` and removes that document from the ordered commit entirely, so the ordering rationale — commit the ambient document last, and a failure among the created ones is still answerable by rolling it back — does not cover a document the script chose to settle. Settling the ambient document specifically gives up that remedy for the human's real open model, which is the strongest argument for a notice at each settle.

**What it does change, and must be decided explicitly rather than shipped as plumbing**: a script gains the ability to express per-document, mid-run commit. `ManagedDocumentTransactions` currently states that "there is no per-document success concept for a script to express, and none is invented" — `settle-on-request` invents one. It is the right trade (it is what `try`/`catch` around a `using`-scoped transaction does in every Revit sample), but it widens what one `execute_script` call can express and needs the same treatment §14 gives adoption's widening, including a `notices[]` entry at each settle: committing early is invisible to the script and changes the document's state, and §01 does not permit that silently. `Settle(keep: true)` in particular makes every prior write in that run permanent *retroactively*, so a later failure will not undo them — the honest entry in §14's escapes-the-boundary list is "the filesystem **and this run's rollback guarantee for this document**".

**`open-on-write`, deferred here in the previous revision, is what shipped as `group-always` transaction-on-write above** (#146 Phase 3) — on the first *block*, exactly as this paragraph predicted, with the breaking change to `Level.Create(Document, ...)` taken knowingly and the skill rewritten around it.

**Carried risks, named so they are not rediscovered.** `ITransactionAdapter.CommitFailures` is overwritten on every `Commit()`, so any multi-commit-per-document scheme destroys all but the last failure set — it must become an accumulator before this ships, and it is the only channel carrying a `ProceedWithRollBack` reason. The callback shape inverts `return`: in `using (var t = new Transaction(…))` an early `return` means *never committed*, inside a lambda it means *commit* — a silent-wrong-answer hazard produced by the very shape-similarity that makes the API learnable, and one to pin with a test. Nested `WithTransaction` on the same document must be specified rather than left to Revit's raw refusal, since every Revit sample wraps each helper method in its own transaction. Per-block commits fire `DocumentChanged` and any other add-in's `IUpdater` N times rather than once, and a later group rollback reverts their edits but not their side effects. **A settled entry's lifecycle is unspecified and the existing unwind assumes it cannot happen**: `CommitAll`/`RollBackAll` walk every `Entry` and call `Commit`/`Assimilate`/`RollBack` plus `Dispose` on each, so a settled document's already-terminal pair would be operated on a second time — `RollBack()` on an assimilated group being exactly the invalid case those methods' comments warn about. Either `Settle` deregisters the entry or the unwind learns to skip settled ones, and `Open`'s `DocumentId` guard must stop refusing the re-open a post-settle write needs. **And a mid-scope forced rollback needs defined behaviour**: `Commit()` returns `RolledBack` when the preprocessor forces `ProceedWithRollBack` on an error-severity failure, which today is terminal for the run — inside a scope it happens mid-script, so without an explicit throw-into-the-script or a notice, the script's writes vanish and it keeps running unaware. And a forgotten `Settle` before `Close` yields Revit's raw refusal, so `ModificationOutsideTransactionException` and its lifecycle siblings need §01 remedy mappings — mapped by type **name**, not by a `catch (Autodesk.Revit.Exceptions.…)` clause in `MCPBridge.Core`. The reason is not that Core lacks the reference — `MCPBridge.Core.csproj` already carries `RevitAPI`/`RevitAPIUI` for `ScriptGlobals`' sake — but that a catch clause forces the type to resolve when its containing method is JITed, which fails in the tier-1 host and takes the whole assembly with it, silently, at `dotnet test` exit 0.

### Long-running scripts & polling

`execute_script` takes an optional `timeout_ms` parameter (sensible default, e.g. 30000, if omitted). A script that finishes inside the timeout returns the normal completed result inline — no change from the common case. One that doesn't returns either `{status:"pending", execution_id}` or `{status:"running", execution_id}` instead of hanging the MCP call — see the distinction below — and a companion command, `poll_execution(execution_id, timeout_ms?)`, is called however many times it takes — same shapes — until the script actually completes or errors.

> **`pending` vs. `running`.** `ExternalEvent.Raise()` only executes when Revit is idle — it won't fire while the user is in an active edit mode (sketch editor, an in-canvas command) or while a modal dialog is pumping its own message loop. Conflating "queued, waiting for the UI thread to free up" with "actually executing" would mislead the agent, since the first case may resolve on its own shortly and the second is genuinely stuck. The add-in knows which is true — whether `Execute()` has been entered yet — so it reports `pending` until execution actually starts, then `running`. A script stuck at `pending` behind a blocking dialog is the same underlying situation as §07's non-framework-dialog fallback, not a separate problem.

> **Instance busy state.** Because Revit's UI thread runs one script at a time, a timed-out-but-still-running script leaves the whole *instance* occupied, not just that call. A second `execute_script` issued against the same instance while one is still in flight returns `{status:"busy", execution_id}` pointing at the existing run, rather than queuing silently or appearing to start a second execution — the agent is told to poll the one already running instead.

### Cancellation — cooperative, with an honest fallback

There is no safe way to force-stop arbitrary running C# on Revit's UI thread — .NET has no safe thread-abort mechanism, and forcibly killing mid-API-call execution would likely leave document state corrupt. Cancellation is therefore cooperative by design, with a distinct terminal state for the case that doesn't cooperate, rather than pretending either alone solves it:

- **Cooperative path.** The script globals object exposes a `CancellationToken` alongside `Document`/`UIApplication`/`UIDocument`. A script checks it between API calls or at loop boundaries; `cancel_execution(execution_id)` signals it. A script that observes the signal and unwinds gets its transaction rolled back cleanly and resolves to a new terminal status, `cancelled` — distinct from `error`, since the agent asked for this. `describe_function`/example content should actively teach agents to check the token in any loop-shaped script.
- **`max_duration_ms`.** A second, separate parameter on `execute_script` — a hard ceiling on total runtime, independent of the polling `timeout_ms` above (default generous, e.g. 10 minutes). When it elapses, the broker auto-issues the same cancellation signal on the agent's behalf, so a script nobody's actively polling doesn't sit forever silently occupying the instance.
- **The fallback, for scripts that don't cooperate.** Cancellation starts a grace timer (default ~5–10s). If execution hasn't actually stopped by the time it lapses — the script ignored the token, or is blocked in unmanaged/blocking code the token can't reach — the instance's status flips to a new terminal value, `unrecoverable`, both in `poll_execution`'s response and in `list_instances`' `status` field (§05), provided the connection that was asked to cancel is still the instance's current one when the grace period lapses — a dropped or replaced connection isn't evidence of a wedged Revit, and escalating on one falsely bricked a healthy instance until restart (issue #47; the phantom execution such a drop leaves behind settles instead via the broker's `execution-lost` path on the first post-redial poll). Further calls against that instance return an explicit error pointing at that state rather than queuing or reporting `busy` — the agent is told plainly the instance needs Revit restarted, not left polling a dead end. Recovery is just a normal restart, which mints a fresh `instance_id` (§05), so the unrecoverable entry naturally ages out of the registry with no special teardown logic — and in the dev environment, exactly what the `prlctl`-driven automation in §13 already does between corpus runs.

### Roslyn isolation & memory lifecycle

Shipping `Microsoft.CodeAnalysis` inside Revit's process, and compiling a fresh assembly per script, has two failure modes that only show up under real usage rather than a quick smoke test — both are addressed the same way, with a custom **collectible `AssemblyLoadContext` (ALC)**:

- **Version collisions with other add-ins.** Other add-ins active in the same Revit process — scripting or automation tooling of the kind commonly installed alongside a plugin like this — may bundle their own, different version of `Microsoft.CodeAnalysis`. .NET resolves an assembly identity once per load context; loading MCP Bridge's Roslyn dependencies into the process's default context risks colliding with whatever another add-in already loaded there. Fix: MCP Bridge loads its own Roslyn dependencies, and every script it compiles, into a dedicated custom `AssemblyLoadContext` it owns — isolated from the default context and from whatever any other add-in does there.
- **Per-script memory growth.** Agent-authored scripts are rarely byte-identical, so a session-lifetime cache of compiled `Script<T>` objects barely hits and each unique script leaves a permanently-loaded assembly behind — a slow leak under exactly the iterative usage this product is for. Fix: each execution's compiled output loads into its own short-lived, **collectible** ALC that is unloaded once the execution completes and its result is captured, so that script's memory is reclaimable by the GC rather than retained for the life of the session. A small bounded LRU (e.g. last 20–50 unique scripts) still caches the compilation itself for the case an agent deliberately re-runs something verbatim — bounded, not indefinite, unlike the original design.

## 07. Modal dialog suppression

The mechanism is `UIControlledApplication.DialogBoxShowing`, registered once in `OnStartup`. It fires before a `TaskDialog` or Revit-framework message box renders; the handler casts the event args to `TaskDialogShowingEventArgs` or `MessageBoxShowingEventArgs` and calls `OverrideResult(id)` with the desired button ID, dismissing it without ever painting a window.

> **Known limitation.** This only catches dialogs raised through Revit's own dialog framework. Third-party add-ins or raw Win32 `MessageBox.Show`/custom modal WinForms windows bypass the event entirely and can still hang the thread. v1 cannot promise 100% coverage.

Default policy: auto-answer with the "safe"/non-destructive option (typically Cancel/No) unless the script explicitly opts into a different per-call policy — an agent running an unattended script should never have Revit silently choose "Delete" or "Overwrite" on its behalf.

### Transaction failures — the Failures API

The most common dialog class a script actually triggers doesn't come from `DialogBoxShowing` at all. Commit-time warnings and errors — "Line is slightly off axis," "N elements will be deleted," unjoined geometry — route through a separate mechanism, Revit's Failures API: `IFailuresPreprocessor`, `FailuresProcessing`, `Transaction.SetFailureHandlingOptions`. A preprocessor is registered on every transaction the script wrapper opens (§06 already wraps each script in a `Transaction`/`TransactionGroup` — this hooks into that same wrapper), inspects `FailuresAccessor.GetFailureMessages()` at commit time, and resolves them programmatically instead of letting Revit render anything.

Resolution policy follows the observability principle above directly: **warnings are auto-dismissed, errors are not.** Any error-severity failure rolls the transaction back and surfaces as a normal script failure in the JSON-RPC result — the agent sees a real problem it needs to react to, not a silently-forced outcome it never asked for. Every failure the preprocessor touches, warning or error, is reported back in `notices[]` using the shared diagnostic-record shape (§01) even when the script otherwise succeeds — so "this ran, but 3 warnings were auto-dismissed" is always visible, never invisible, and always in the same place an agent would check for anything else auto-resolved.

> **Deferred, not designed away.** A more aggressive policy — confidently auto-resolving specific known error cases rather than always rolling back — is plausible later, the same way this section's non-framework-dialog handling (below) plans an allowlist-driven v2. It isn't designed now because it isn't known yet which specific errors recur often enough to justify a confident default; that list gets built from real usage, not guessed in advance.

### Fallback for non-framework dialogs

Two-stage plan, deliberately sequenced so the auto-dismiss heuristics in stage 2 are built from observed real-world dialogs rather than guessed in advance:

- **v1** On an `execute_script` timeout with no `DialogBoxShowing` event fired, the add-in enumerates top-level windows owned by the Revit process (`EnumWindows` + `GetWindowThreadProcessId` — a Win32 call from the TCP/background thread, not the blocked UI thread; reading window *text* is timeout-bounded per window AND the whole enumeration runs under a hard overall budget, because `WM_GETTEXT` against a same-process window blocks on the very UI thread being diagnosed — unbounded, the diagnostic deadlocked whenever the UI thread was merely busy with a long script, and the per-window bound alone still did, since a busy-but-not-OS-"hung" thread makes hundreds of windows wait their full timeout serially; both found live by the execution-lifecycle harness test. The diagnostic is therefore reachable but possibly *partial*, and says so: a budget-truncated pass sets `inventory_truncated` in the notice's detail and flags it in the message, with timed-out text reported as placeholders rather than silently dropped — §01's observability principle applied to the diagnostic itself) and returns their titles and window-class names as diagnostic data in the JSON-RPC error payload — *no automatic action is taken, and none is possible from v1*. This turns a silent hang into "here's what's actually on screen" for a human to dismiss manually. It is **diagnosis only**: a follow-up `execute_script` call cannot target the stuck window, because that follow-up would also run via `ExternalEvent` on the same UI thread the dialog is already blocking (§06) — it would report `pending` and never execute either.
- **v2** Once real usage has surfaced the actual set of recurring non-framework dialogs (expected culprits: third-party add-in message boxes, native file-recovery/corruption prompts), extend the same window-enumeration pass to auto-dismiss matches against a maintained allowlist of known title/class signatures — `WM_CLOSE` or a simulated default-button click. This has to run from the same background thread as the v1 diagnostic, off the UI thread entirely — it's the only mechanism in this section that can actually act on a stuck dialog, not an implementation detail. Deliberately allowlist-based rather than a blind "close anything modal" heuristic, since misfiring on a legitimate window is worse than leaving it to the v1 diagnostic.
    - **Shipped (#134).** The allowlist mechanism landed with exactly one entry, `WM_CLOSE`-only (no button click, no "do not show me this message again" tick): class `#32770` + title `"Virtual Memory - High Usage"` — Revit's own low-memory warning, surfaced twice by real usage (#129), a raw Win32 box the framework `DialogBoxShowing` suppressor cannot see. `DialogAutoDismissPolicy` (MCPBridge.Core) holds the allowlist as a pure, unit-tested predicate; `Win32WindowInventory` posts the close where the `hWnd` lives; each dismissal is reported as a `dialog-auto-dismissed` `notices[]` record (§01). The report is captured through a side channel so it survives the v1 pass's own wire-budget cap (#138). Adding a future entry is one line in the policy — but each new signature still needs a live-verified exact class+title and one unambiguous safe outcome, the bar this section sets.

## 08. API discovery tools

No surveyed project implements this — it's the clearest gap in the field. Revit ships `RevitAPI.xml` and `RevitAPIUI.xml` next to the DLLs: standard .NET XML-doc sidecar files containing `<summary>`/`<param>`/`<returns>` for every public member — the same source Visual Studio IntelliSense reads. Combined with reflection over the assemblies, this powers all three commands with zero external dependency or network access:

| Command | Implementation |
|---|---|
| `list_functions` | One-level-at-a-time tree over a persistent cache of `RevitAPI.dll`/`RevitAPIUI.dll` (plus any other loaded add-in's API): no args → namespaces; `+namespace` → type names; `+namespace+type` → member names. See "Response size & pagination" below. |
| `search_functions` | Semantic hybrid ranking in the **broker** (issue #107): BM25F + static sentence embeddings over member names, namespaces and summaries, fused by reciprocal rank, cross-encoder reranked. The add-in only ships the corpus (`dump_members`). |
| `describe_function` | Full XML-doc entry (summary, params, returns) joined against the reflected signature for one fully-qualified member. |

> **Known gap.** `RevitAPI.xml` doc comments are often terse compared to community docs (revitapidocs.com, The Building Coder). v1 ships on the shipped XML alone — sufficient for "what does this method do and what does it take," insufficient for worked examples. A curated example corpus is a plausible v2 addition, sourced from the same tutorial pool as the test corpus (§13), not from the XML.

### Execution locus — live reflection, backed by a persistent cache

Reflection over `RevitAPI.dll`/`RevitAPIUI.dll` doesn't touch the Revit API context at all — no `Document`, no `UIApplication` — so unlike `execute_script` it never needs `ExternalEvent` or the UI thread. Served on the add-in's background connection thread, discovery is simply never subject to the busy/pending state machine in §06 in the first place; a script running on the UI thread has no bearing on it. There's still a language-mismatch reason the add-in has to be the one doing this rather than the broker — the broker is Go (§04) and can't reflect a .NET assembly — but that's the only thing that has to live in the add-in:

- `describe_function` is a single reflected member plus its matching XML-doc node — trivially cheap, live or cached.
- `list_functions`/`search_functions` stay fast because they're scoped by namespace/type or ranked top-N (below).

> **Revision — a persistent SQLite cache, not pure live reflection every call.** The original design here reflected fresh on every call and explicitly rejected a persistent index ("a second, driftable source of truth alongside the live DLL... not worth it to close a narrow case"). Live measurement changed that calculus: enumerating the type list alone cost ~1.5s and a first full-corpus `search_functions` scan cost ~700ms, paid again on every single Revit process launch with nothing carried over — a real, repeated cost, not a narrow edge case. `MCPBridge.Core.Discovery.DiscoveryCache` (Microsoft.Data.Sqlite + FTS5, at `%LOCALAPPDATA%\Connectors\Revit\discovery-cache.db`) now persists the reflected surface across restarts. It stays a cache, not an independent source of truth: `DiscoveryCache.Sync` diffs currently-loaded assemblies against what's stored by file hash on every add-in startup (plus one deferred re-check ~8s later, to catch add-ins that finish loading after `OnStartup` returns — Revit doesn't guarantee load order) and reconciles automatically, so drift self-heals on the next launch rather than accumulating. `search_functions` also gained a real FTS5-backed ranking in the same change, replacing the previous full-corpus hand-rolled scan the ~700ms figure above measured.

- The trade-off from the original design is unchanged: discovery needs **at least one Revit instance connected at least once** to populate the cache in the first place — it can't answer before Revit has ever been launched. What changed is that this population now survives across restarts instead of being paid again every time.

> **Deferred — a pre-indexed function graph.** `list_functions` specifically has a plausible future case for a real, precomputed index — not for availability or speed (the cache above already covers that), but for capability: cross-referencing relationships live reflection doesn't cheaply answer per-call, like "what methods return this type" or "what constructs consume it." Worth revisiting once real usage shows that kind of graph-navigation query actually comes up; not designed now, same as the other v1/v2 splits in this doc (§07 twice, and the example corpus above).

### Response size & pagination

Revit's public API surface is roughly 1,700 types — an unscoped `list_functions` call would be a multi-megabyte answer, and "progressive disclosure" is the entire point of these commands, so dumping everything defeats the design as surely as not having discovery at all. Concretely bounded by the same ceiling confirmed for this project's MCP client elsewhere in this doc (§09): Claude Code caps MCP output at 25,000 tokens by default.

`list_functions` is a strict one-level-at-a-time tree rather than a flat, scopable member dump: called with no arguments it returns namespace names only (with a per-namespace type count); given a `namespace` it returns that namespace's type names (namespace-prefix-stripped, as a single comma-separated string); given `namespace`+`type` it returns that type's distinct member names (own + inherited, type-prefix-stripped, also comma-separated) — `type` without `namespace` is a params error, not a silent resolution. Every tier is paginated (a cursor for more) even though the top tier in practice fits in one page. `describe_function` is the only way to get full per-member detail (signature, summary, params, returns) — deliberately, so browsing stays cheap and full detail is always a single explicit follow-up call, never bundled into a list response by default.

`search_functions` returns a bounded, ranked top-N (default ~20) with the same cursor pattern, and accepts an optional `namespace` filter (same scoping semantics as `list_functions`, applied before ranking). Ranking is tiered, highest first: an exact `Type.Member` match; then all query tokens matched across the member's own name and its declaring type's short name (not the summary) — what makes a query like "wall create" reliably surface `Wall.Create`; then FTS5's own BM25 ranking against name+summary+type name combined, for looser/exploratory queries. `describe_function` is inherently single-member scoped and doesn't need pagination, though a member with many overloads returns compact signatures for all of them by default rather than the full XML-doc entry per overload, to stay well under the ceiling on the common case.

> **Revision — ranking moved to the broker (issue #107, `revit/docs/search-ranking-redesign.md`).** The tiered/FTS5 ranking above is what the add-in still computes, but `search_functions` no longer serves it except as a fallback. The recall failure mode was structural: a task ("get every wall in the document") and the member that answers it (`FilteredElementCollector.OfClass`) often share no token, and an agent reads an empty keyword result as "the API is absent". The ranker now lives in the Go broker, version-independent and testable without Revit: on instance attach the broker pages the whole documented corpus from the add-in (`dump_members`, keyed by a fingerprint of the loaded assembly set so identical corpora share one index), builds a BM25F index and a per-field static sentence-embedding index (model2vec `potion-base-8M`, pure Go, ~1.4s for the 76,601-member 2027 corpus), and at query time fuses both by reciprocal rank, masks the `BuiltIn*` enum floods and any `namespace` scope *before* ranking, and reranks the top 20 with an int8 `ms-marco-MiniLM-L-6-v2` cross-encoder (~1.2–1.5 s on an M1 Max, also pure Go via hugot/GoMLX). Both models are embedded in the broker binary (+~68MB; fetched at build time against sha256 pins, never committed), so §04's single-binary promise holds; a build without them ranks lexical-only and says so in every response. Measured in Go on 43 labelled task-style queries against the real 2027 corpus (`TestRealCorpusRecall`): recall@1 / @3 / @10 of 24 / 29 / 34 out of 43 for the shipped pipeline, against 14 / 21 / 28 for its keyword stage alone (the Python POC that chose the design measured 23 / 29 / 33 and 14 / 20 / 26 for the same two). The transformer bi-encoder the POC used (BGE-small) was rejected for the shipped design because pure-Go inference embeds ~14 members/s — hours per index — whereas the static model matched it once the cross-encoder ran. Until an instance's index is built (seconds), or if the models are missing, the response's `ranker` field says which ranker answered. The `query` schema now asks for one plain sentence naming the element type and operation, which is the input all three stages want.

### Multi-version disambiguation (§11)

Once instances of different Revit versions can be connected at once, an unscoped discovery call (no `instance_id`) is no longer safely arbitrary — 2025's and 2027's reflected API surfaces genuinely differ (confirmed live: 557 vs. 724 scoped namespace entries against the two real installs), so silently picking a connected instance would hand back version-specific data with nothing telling the caller it's version-specific, and non-deterministically across repeat calls as connections come and go. The broker's `discovery.Router` resolves the target connection with a read-only reference into the instance registry (§05): if `instance_id` is omitted and every connected instance shares one Revit version, that version is picked as before; if the connected instances span more than one version, the call errors (`ambiguous-instance-version`) with a candidates list (`instance_id` + `revit_version` per connected instance) instead of guessing — deliberately not "merge results across versions," which would create a false single-surface impression and force every caller to reason about namespace/type overlap between two genuinely different APIs. Every discovery response, scoped or not, also carries the resolved instance's `revit_version` so a caller that let the broker pick can still tell which version answered without a separate `list_instances` call.

## 09. File exchange

No established convention exists for CAD-tool-to-agent file exchange — this is original design, not a researched pattern. Keyed by document identity rather than instance PID, so relative paths an agent has already referenced stay valid across a save/reopen (PIDs are ephemeral, document identity isn't).

The workspace tree lives under a **separate root from the rest of this add-in's app data**, deliberately: `imports/`/`exports/` are content a human is meant to browse and manage directly with their own filesystem tools (below), unlike `broker.json`/`instances.json`/the discovery cache (§08), which are internal bookkeeping nobody browses and stay exactly where they already are. Burying human-facing files in `%LOCALAPPDATA%` alongside that internal state would work but be needlessly unfriendly, so the workspace root is `%USERPROFILE%\RevitMCPExchange\` instead — visible in a normal Explorer session, not three folders deep in an AppData path. Shown below for local mode; in remote mode the add-in writes the identical structure rooted at the shared folder instead (e.g. `\\Mac\connectors\RevitMCPExchange\...` — this project's own dev environment's actual working UNC path as of this writing; see §13's note on the alias's history of changing across restarts), per §05.

```
%LOCALAPPDATA%\Connectors\Revit\        # internal bookkeeping — never browsed by a human
  instances.json                        # live registry: instance/doc → connection state
  <revit-version>\discovery-cache.db    # §08

%USERPROFILE%\RevitMCPExchange\         # human-facing — the file-exchange workspace tree
  <document-id>\
    imports\                # files placed here for a script to consume; never auto-deleted
    exports\                # images, IFC, families written by scripts; never auto-deleted
    logs\                   # per-execution NDJSON logs, timestamped — one shared diagnostic-record shape (§01) per line; age out
    scripts\                # history of executed script text, timestamped; age out
    tmp\<instance-id>\      # scratch, per instance sharing this workspace; ages out with the audit sweep
```

Retention splits by ownership, not by a uniform rule: `imports/`/`exports/` hold content someone deliberately asked for — a human's upload, a script's requested output — and auto-deleting either would be a far worse surprise than the disk space they cost, so they're purely user-managed via normal filesystem tools and the sweep never visits them. `logs/`/`scripts/` are audit-trail bookkeeping nobody asked for and nobody owns, generated on every execution that reaches the script executor (a run refused before a document was resolved has no routed workspace to write into, and its refusal is fully carried by the §01 error path) — those, plus `tmp/<instance-id>/`, age out after **14 days**, deleted by a once-per-process background sweep triggered from the first audited completion (`ExecutionAuditTrail`; issue #13 — deliberately not a timer service to own). An earlier draft of the tree said `tmp/` was also "cleared on document close"; it is not, deliberately: `DocumentClosed` carries only Revit's internal integer id, so the §09 identity is unrecoverable once the document is gone, and pairing the cancellable `DocumentClosing` event with it just to delete scratch days earlier than the sweep fails the same not-worth-the-machinery test as the timer.

Scripts reference files by path relative to their document's `RevitMCPExchange/<document-id>/` root; the broker resolves these into an actual path in every MCP tool response, per the mechanism below. Every `execute_script`/`poll_execution` result also carries a `files[]` array alongside `notices[]` (§01) — one entry per file the script published as an output (below), each with its own per-file `status`, never a single aggregate success/failure for the whole set.

### Getting bytes to the agent

A resolved path is not the same thing as file content — whether the agent can act on a bare path depends on whether it has its own filesystem access to wherever that path points, and neither of the two obvious transfer mechanisms (embedding content in a JSON-RPC response, or MCP resources) handles a large export gracefully: both would force a full binary blob through a single stdio message, materialized in memory on both ends, for a payload that couldn't usefully enter the agent's context window anyway even if it arrived. So large-file exchange is designed around *not* routing bytes through MCP at all, wherever possible:

- **Primary mechanism — shared filesystem.** In local mode this is automatic: the workspace directory is already on the one disk everything shares. In remote mode it's the same fix already used for this project's own dev environment — a Parallels shared folder, referenced by its **UNC path** (`\\Mac\connectors\` as of this writing on the Windows/VM side; the alias itself has changed once already across a Parallels restart — was `\\psf\connectors\`, see §13 — so treat either as re-resolvable, not permanently fixed) rather than a locally-mapped drive letter, since drive-letter assignment isn't guaranteed stable either — Parallels' own default "Home on 'Mac'" share and the connectors share both get assigned letters (confirmed: `Z:` and `W:` respectively in this environment) that could reassign on a reboot or reconfiguration, which is exactly why the UNC form is what's actually used, never a letter. The broker, which knows both roots, rewrites every path the add-in reports (Windows-native) into the agent-host-native form (e.g. `\\Mac\connectors\RevitMCPExchange\doc-1a2b\exports\view.png` → `/Users/.../connectors/RevitMCPExchange/doc-1a2b/exports/view.png`) before it ever reaches the agent. The agent then reads the file with its own filesystem tools, entirely outside the MCP channel — no size limit, no memory-doubling, genuinely graceful for a 1GB export.
- **Fallback — `read_file(document_id, relative_path, offset?, length?)`.** For the case with no shared filesystem at all. Chunked/range-based from the outset, never whole-file-in-one-response; a request exceeding a configurable size threshold with no range specified is rejected with guidance to use the shared-path mechanism instead, rather than attempting the transfer and choking on it.
- **MCP resources** are optional polish for hosts that support them, layered on the same chunked-read primitive — not the primary mechanism. Confirmed: Claude Code does support `resources/list`/`resources/read` (referenced via `@server:protocol://path`), but caps MCP output at 25,000 tokens by default (500,000 characters even with an explicit size declaration) — roughly 100–350KB depending on encoding, nowhere near a 1GB export. This isn't a gap in Claude Code's support; it confirms resources were never going to be the large-file mechanism regardless of host, which is exactly why the shared-filesystem path above is primary and not a fallback.

> **Scoped out of the current implementation pass.** `read_file` and MCP resources only have a real trigger condition when the agent host has no direct filesystem access to the shared workspace at all. Remote mode now exists and is exercised for real (this project's own Mac+Parallels dev topology), but its actual case — a Parallels shared folder the Mac host already mounts directly — still gives the agent's own host direct disk access, the same as local mode. Neither mechanism is built yet; document identity, the workspace tree, and `Publish`/`files[]` below are the actual current build. Revisit if a real remote-mode setup surfaces without a shared filesystem at all.

### Uploading files to a script

The reverse direction is deliberately the mirror image of the download story above, for the same reason: an agent has no business piping a large file's bytes through a JSON-RPC message any more than it has business receiving them that way. There is no `upload_file`-style tool that accepts file content as a parameter. Instead:

1. The agent-side host places the file(s) into `imports/` using its own filesystem tools, resolved through the same shared root as everywhere else in this section (in local mode this is trivial, since the workspace is already on the one disk everything shares; in remote mode it's the same UNC-path mechanism used for exports above, just written instead of read).
2. The agent calls `execute_script` with a script that reads from the now-present path under `imports/` via ordinary `System.IO` — no different from a script reading any other file it was told about. A script doesn't need to be told or construct that path itself: the globals object §06 already exposes `Document`/`UIApplication`/`CancellationToken` through also exposes `ImportsDirectory` (alongside `ExportsDirectory`, below) directly, so a script can do `System.IO.File.ReadAllBytes(System.IO.Path.Combine(Connector.ImportsDirectory, "model.csv"))` without the agent needing to know or embed the workspace's absolute path.

Because "the user should be able to upload or download multiple files, though a single file is by far the more common case" was an explicit requirement, both directions are batch-shaped from the outset rather than a single-path parameter with a list bolted on later: a set of files, not one file, is the base case, and per-file status (below) is what a batch of independent file operations naturally needs.

### Publishing script outputs

A script doesn't construct an `exports/` path itself — it calls `Connector.Publish(path, name?)`, on the connector's own API object that §06 exposes in script scope alongside `Document`/`UIApplication`/`CancellationToken` (see §14, "The connector's API is an add-in API"). `Publish` copies (never moves — a script may still want to reference or log its own working file afterward) the file into that document's `exports/` directory and registers it for the response; if the script already wrote directly into `exports/`, `Publish` recognizes the file is already there and just registers it rather than copying it onto itself. Every registered file becomes one entry in the result's `files[]` array (above), each with its own `status` — a failure on one file (disk full, a locked target, a bad source path) never rolls back or blocks the others, the same per-file-independence reasoning behind the upload/download batching above.

**Collisions** are controlled by `overwrite_output_files` (default `false`), a request-level flag on `execute_script` applied uniformly across every file `Publish` touches during that run — not a per-file override, which would be more mechanism than this needs. With the default, a `Publish` call that would overwrite an existing file becomes a `status: "failed"` entry with a message naming the flag, never a silent skip (§01) and never an abort of the rest of the batch. Most real usage is iterative — an agent re-running a script against the same output name expects to overwrite — so `overwrite_output_files: true` is expected to be the common case in practice; the default stays `false` regardless, since a script silently clobbering a prior export is a worse surprise than an explicit failure asking for the flag.

### Browsing a workspace

`list_workspace_files(document_id, subdirectory?)` returns an array of `{name, size, modified_at}` for one workspace directory — metadata only, never content, the same restraint as everything else in this section. It exists so an agent can discover what's already in `imports/`/`exports/` (e.g. confirming a human's upload landed, or checking what a prior script run already produced) without needing a script round-trip just to list a directory.

> **Scoped out of the current implementation pass**, for the same reason as `read_file` above: in local mode, the agent's own host already has direct filesystem access to the workspace tree and can list a directory with its own tools — a script round-trip (`Directory.GetFiles(...)` returned as output) already covers this today with nothing new to build. This tool earns its keep once remote mode exists and that direct access goes away.

### Document identity

`document_id` is not one thing — Revit documents show up in four states that each need a different identity source, and the source has to be something stable enough to survive a re-open, not just "whatever path is open right now":

| Document state | Identity source | ID form |
|---|---|---|
| Saved, non-workshared | Local file path, compared case-insensitively (`OrdinalIgnoreCase` — Windows paths are case-preserving but not case-sensitive); a mapped network drive letter is resolved to its UNC target first (`WNetGetConnection`, best-effort — the same P/Invoke-with-safe-fallback pattern §07 already uses for its window-enumeration fallback) so the same file opened via `Z:\House.rvt` and `\\server\share\House.rvt` still hashes identically | `doc-<hash>` |
| Saved, workshared (local or cloud/ACC central) | **Central model path** (`Document.GetWorksharingCentralModelPath`) or cloud model URN — never the local copy's path, which is per-user and regenerated on every fresh local copy | `doc-<hash>` |
| Unsaved / new / detached-and-not-yet-saved | No stable path exists yet — session-scoped GUID minted on open | `tmp-<guid>` |
| Family document (.rfa) | Same rules as above, applied to the family file's own saved/unsaved state | `doc-<hash>` or `tmp-<guid>` |

The `doc-`/`tmp-` prefix is deliberate — it's visible in every `list_instances` response and every workspace path, so an agent (or a human debugging) can tell at a glance whether a given ID is durable or session-only without a lookup.

> **Promotion on first save — simplified from the original design.** An earlier version of this section specified renaming the workspace folder in place plus a short-lived old-id-to-new-id alias on a `tmp-` document's first save. Independent PR review found that design unreachable in practice — identity is only re-resolved on the next `register`/`execute_script` call after the save, by which point the old workspace folder the rename would have targeted was never the one anything actually wrote into (see the file-exchange PR's own fix for why identity must be resolved once and cached per live document, not recomputed per call) — and found the alias was never consulted anywhere in production. The actual, simpler behavior: a `tmp-` document's already-published files stay under its `tmp-` workspace for the rest of that session; once re-resolution picks up the save (a fresh `doc-<hash>`), the document gets a new workspace going forward, with no rename and no alias. A later Save-As to a different location behaves the same way. Real rename-in-place promotion remains a plausible future enhancement if this proves to matter in practice — not designed now, matching this doc's other v1/v2 splits.

> **Closed gap — a `tmp-` ID is now stable across API call sites** *(v1 remediation series; became load-bearing the moment `document_id` routing shipped)*. The history: the per-document cache is a `ConditionalWeakTable` keyed on the Revit `Document` wrapper, and live instrumentation established Revit does **not** hand back the same wrapper for the same document across API calls (`Application.Documents` vs. `ActiveUIDocument.Document`: `refEquals=False` for a single open document). Saved documents were immune (path-derived ids), but an unsaved document got an independently minted `tmp-<guid>` per wrapper — `register` advertised `tmp-A` while `Publish` wrote into `tmp-B`'s workspace, and once routing existed, a request for either id could never match reliably (caught live by the routing harness test, exactly the failure shape predicted here). The fix is the wrapper-independent key this note always called for: an unsaved document's id is now derived from a per-process salt plus its **title** — Revit auto-uniquifies open documents' titles, a title only changes on save (when the id becomes path-derived anyway), and the salt keeps ids session-scoped and distinct across concurrent instances. Accepted nuance: closing an unsaved document and later creating another with the same title in the same session reuses the id/workspace — session-scoped scratch, consistent with `tmp/`'s retention story. A document whose Title accessor throws mid-transition falls back to a per-wrapper GUID, held stable by the cache.

### Shared workspaces & linked models

- **Two instances, one workspace.** Two Revit instances opening the same central model (or two local copies of it) legitimately produce the same `doc-<hash>` — that's correct, since the workspace is keyed by document *content identity*, not by instance. `exports/`, `logs/`, and `scripts/` already avoid collisions on their own, since every entry is timestamped per execution; `tmp/` is the one directory that isn't, so it gets an `instance_id` subfolder (`tmp/<instance_id>/`) rather than a shared flat scratch space. `list_instances` (§05) surfaces this directly — an agent looking at two entries with the same `document_id` can see they share a workspace, rather than assuming exclusive access it doesn't have.
- **Linked models don't get their own identity.** A linked document is reference data reached *through* a host document's own API surface (`RevitLinkInstance`/`RevitLinkType`, `Document.GetLinkDocument()`-style calls) inside a script's globals — it's not something an agent addresses directly the way it addresses `{instance_id, document_id}`. It gets no `doc-`/`tmp-` ID, no workspace directory, and no `list_instances` entry; a script that needs to touch a link does so via the host document it already has open, the same way any other Revit API code would.

## 10. Security model

`execute_script` is full code execution inside the Revit process, by design (§02). That makes the transport-level defaults non-negotiable even though the script trust model itself is deliberately unsandboxed:

- In **local mode** (§05, the target deployment) the broker binds to `127.0.0.1` only — never `0.0.0.0` — which is the actual protection, since nothing outside the machine can reach the port at all.
- In **remote mode** (§05) the broker binds a specific non-loopback interface by necessity, so loopback can't be the safeguard — the token below is what actually carries the weight there.
- The **broker** — not the add-in — generates a random token whenever it wins the singleton lock and becomes primary (§05), and writes it into the same `broker.json` it already publishes for discovery. Every connecting party (Revit add-ins, and secondary broker processes acting as agent-client proxies, §05) must present it on first message before any other command is accepted — this closes the specific hole where an unrelated local process could register as an agent-client and drive `execute_script` for free.
- **Honest limit:** since `broker.json` is readable by the same OS user in local mode, a genuinely malicious same-user process could read the token out of it too — the token doesn't add a boundary *within* the same-user-local-trust model already assumed here, it only filters accidental cross-talk from unrelated software. In remote mode, though, it's the only real protection the port has, which makes remote-mode security bounded by who has access to the shared drive (§09) the token now rides on — a real, named limitation, not hidden.

## 11. Multi-version strategy

Revit 2025 moved the API to .NET 8 (from .NET Framework 4.8) — a hard runtime break, not a compatibility shim situation. **Corrected during Phase 1 implementation, verified directly against the installed product**: Revit 2027 specifically requires .NET 10, not .NET 8 — `RevitAPI.runtimeconfig.json` declares `"tfm": "net10.0"` with a `Microsoft.NETCore.App`/`Microsoft.WindowsDesktop.App` version 10.0.0 requirement, and the add-in fails to compile under `net8.0-windows` against the real `RevitAPI.dll`/`RevitAPIUI.dll` (a hard `CS1705` assembly-version conflict, not a suppressible warning). v1 targets 2027 only, now on `net10.0-windows`; the project is still structured as a multi-target `.csproj` (`<TargetFrameworks>`) from day one, but the assumption that 2025/2026/2027 all share one .NET generation no longer holds — Autodesk evidently bumped the runtime again between the 2025/2026 generation and 2027. **2025 verified directly**: with Revit 2025 installed alongside 2027 on the dev VM, `RevitAPI.runtimeconfig.json` confirms `"tfm": "net8.0"` (`Microsoft.NETCore.App`/`Microsoft.WindowsDesktop.App` both `8.0.0`) — the original pre-2027-correction assumption holds for 2025 specifically, so Phase 6's `net8.0-windows` target for 2025 is confirmed, not just assumed — and has since **shipped and been live-validated** against a real 2025 install (§15 phase 06), so the project now genuinely builds and runs on two TFMs rather than one, even though v1's own scope above remains 2027. **2026 remains genuinely unverified** (not installed on this VM) — per the same lesson 2027 already taught this project, don't assume it matches 2025 just because they're adjacent releases; verify it directly the same way before Phase 6 adds a 2026 target.

## 12. Signing & distribution

Unsigned add-ins load in Revit today, with an "untrusted publisher" warning on every startup — itself a modal dialog worth suppressing during early internal testing, separate from the general dialog-suppression story. Signing is an Authenticode signature on the compiled DLL only (the `.addin` manifest XML is never signed), applied via `signtool.exe` as a post-build step; timestamping is required so the signature doesn't lapse when the certificate itself expires.

There's a relevant precedent among widely-used Revit scripting tools: the most established one has never been distributed through the Autodesk Marketplace, shipping instead as a signed installer from GitHub Releases with its own extension registry layered on top — a durable end-state, not just a stopgap. Its own maintainers, asked directly whether it could go on the App Store, had no official answer beyond a guess of "probably not." v1 follows the same path; Marketplace submission is deferred to a later milestone and treated as genuinely uncertain rather than a formality (§14).

### Installation UX — a PowerShell script, not a GUI installer

That precedent's own installer is a packaged GUI (Inno Setup) — but its update story splits in two: the core app needs the installer re-run for a new version, while installed extensions update in place via `git pull` against their own repos. Neither half of that transfers cleanly here: our extension surface isn't interpreted Python re-read on each launch, it's a single signed, compiled DLL, so there's no "just pull new files" path at all — every update, small or large, means replacing that DLL.

Given that, a full GUI installer buys less than it costs. The chosen path is a single PowerShell script (`Install-MCPBridge.ps1`), run either as a downloaded file or piped directly (`irm .../install.ps1 | iex`, matching the same pattern this project's own dev tooling already leans on via `dotnet-install.ps1`):
- **Self-upgrade reuses the exact same code path as install** — there is no separate "installer mode" vs. "updater mode" to design or maintain; the script is idempotent by construction (see below), so the ribbon's update click just re-invokes it.
- **Less to build and sign.** No separate installer-authoring toolchain; only the add-in DLL itself needs the Authenticode signature (already required regardless, per this section's first paragraph).
- **Matches the audience.** Anyone installing a connector that lets an AI agent run C# against their live Revit session is already past the comfort level a GUI wizard exists to protect.

The tradeoff, accepted deliberately: no automatic Programs & Features entry (the script writes one itself — an uninstall registry key under `HKCU`/`HKLM:\...\Uninstall\` pointing back at a `-Uninstall` invocation of itself), and a downloaded-then-double-clicked `.ps1` still hits PowerShell's execution-policy gate (the piped one-liner doesn't, since policy checks apply to script *files*, not piped content) — worth documenting the piped form as primary and the downloaded form as the fallback for anyone who wants to read it first, which this audience often will.

### Self-upgrade

The two components have genuinely different update stories, because only one of them is something Windows can hold a file lock on:

- **MCP Server (Go broker)** is a normal long-running process — nothing has it locked. It can check GitHub's latest-release API itself and a single click can download-and-relaunch the new binary immediately, no restart of anything else required.
- **MCP Bridge (the add-in DLL)** is loaded for the whole Revit session; it cannot be hot-swapped while Revit is running. The realistic ceiling on "one click" here is: detect the update, download it silently in the background, then one click either closes and relaunches Revit right away or defers to Revit's own next natural restart — "one click" means *one click commits to it*, not that the loaded DLL is patched in place.

Both are driven by the same install script (`-Update -Silent` for the non-interactive, ribbon-triggered case). The UX surfaces through the ribbon Status button already built for connection/build-identity display (§04's "intentionally thin" exception) rather than any new UI surface — extended with an "Update available (vX.Y.Z)" state, sourced from a version field added to the same status the add-in already polls from the broker.

**Idempotency is load-bearing, not incidental** — the same script runs unattended from the ribbon, so re-running it with nothing to do must be a true no-op: one `GitHub` API call, a version-string comparison against a locally-written marker, done. That comparison must check the *actual deployed DLL's presence*, not just the version marker — a marker claiming "current" while the DLL is missing (deleted by hand, a failed prior run, AV quarantine) must trigger a repair, not a silent no-op that leaves a broken install unfixed forever. Three outcomes, not two: version matches + DLL present → true no-op; version matches + DLL missing → repair (redeploy, logged as a repair, not a version bump); version differs → normal update.

### Multi-version installs

Revit's own `AddInLoader` already isolates this for us: `Addins\<year>\` is a separate folder per major version, and Revit only loads manifests from the matching year's folder (§04's deployment-location finding, extended). The script detects every installed Revit version and deploys to each one's Addins folder automatically, with no "which version?" prompt — cheap to do, and asking would be pure friction. It's bounded to versions we actually ship a build for: today that's 2027 only, so a detected-but-unsupported 2026 install is skipped with a note, not attempted. §11's already-flagged multi-version runtime split (2027 needs .NET 10; 2025 needs .NET 8; 2026 unverified) means those future variants are genuinely different builds per version, not copies — the release artifact will need one build per supported version-TFM once Phase 6 lands, which the install script's per-version loop already accommodates without needing a rewrite.

One update-flow wrinkle worth deciding now: an update click must not force-close every open Revit across every installed version just because one of them triggered it. The script should only redeploy to version-folders whose `Revit.exe` isn't currently running, leaving any version that IS running to finish updating on its own next restart — a partial "2026 updated, 2027 will finish next restart" outcome, not an all-or-nothing shutdown.

**Installed on multiple versions and usable simultaneously are different claims.** The installer only answers the first: deploying to every detected version's Addins folder says nothing about whether an agent can address a specific one of two concurrently-running Revit instances (say, 2026 and 2027 both open at once) — that's the multi-instance/`list_instances`/`{instance_id, document_id}` routing half of Phase 2 (§15) — implemented as of the v1 remediation series — not something this section solves.

### Mac + Parallels

There is no macOS build of Revit, so this was never a case for a second add-in installer — it's this project's own existing dev topology (§05 remote mode). A Mac-based user runs the Windows install script inside their Parallels VM for the add-in half exactly as above, and runs the MCP Server broker natively on the Mac host in `-mode remote`, pointed at the VM's shared folder. The Go broker already cross-compiles for macOS with no code changes (`internal/singleton`'s `lock_unix.go`/`lock_windows.go` split already exists for this). **`revit/install-mac.sh` now covers the Mac side**: auto-detects the Parallels shared-network IP, builds the broker from source (no release pipeline exists yet — same reasoning as `install.ps1`'s own `-LocalPackagePath` escape hatch), and registers it with `claude mcp add --scope local` — deliberately short, not a redesign of anything above, and live-verified end to end against a real VM-hosted Revit instance.

> **Known gap.** Nothing above works until a release pipeline actually exists to produce what the script downloads: a signed zip per supported version-TFM plus a `checksums.txt`, published to GitHub Releases with a stable asset-naming convention the script can rely on. That pipeline is unbuilt — a prerequisite for shipping this design, not just for writing the script itself.

## 13. Validation & test corpus

Correctness here isn't unit-testable in the conventional sense — the surface under test is "can an agent, given only `execute_script` + the three discovery commands, actually accomplish real Revit workflows." The validation strategy is a growing corpus of test cases drawn from real tutorials, run end-to-end against a live Revit session:

- **Sourcing:** beginner and advanced workflows pulled from Revit API tutorials (Building Coder archive, Autodesk's own API samples, Revit API forum threads, YouTube/course walkthroughs) — each becomes a natural-language task description plus an expected-outcome check (element count, parameter value, exported file exists).
- **Grading:** pass/fail per case, run against an agent that has *only* the four MCP Server tools — no hand-written wrapper tools — so the corpus directly measures whether API discovery is sufficient for an agent to self-teach the workflow.
- **Regression:** re-run the full corpus on every add-in change and before each Revit-version addition, since a passing case today is the guardrail against a future refactor silently breaking dialog suppression or the threading handoff.

### Dev-environment automation

The dev machine (Mac + Parallels running Windows/Revit) is not the target deployment — the common case is Windows-native, Claude and Revit on the same box (§05) — but it does need to run the regression corpus unattended, and needs the remote-mode topology (§05) exercised for real, not just designed on paper. Two pieces of tooling already exist for this rather than being hypothetical: `prlctl` controls VM lifecycle (`prlctl start`/`stop`/`restart`) and can execute commands inside the guest once Parallels Tools are installed (`prlctl exec <vm> ...`), enough to launch/kill Revit.exe and drive a clean-state test loop from the Mac without manual interaction in the VM window; and a Parallels shared folder (`\\Mac\connectors\` on the Windows side as of this writing — the alias has changed once already across a Parallels restart, was `\\psf\connectors\`, so re-resolve rather than assume either is permanent — backed by the repo's own directory on the Mac) is already configured between the two OSes with an agreed root path, which is what §05's remote-mode discovery and §09's file exchange are both specified against. Reference it by UNC path, not a mapped drive letter — letter assignment isn't guaranteed stable across reboots, and Parallels' own default "Home on 'Mac'" share already occupies `Z:` in this environment (the connectors share itself landed on `W:`). (`prlsrvctl` is a separate tool — it configures the Parallels Desktop service/host-level settings, not individual VMs, and isn't the right tool for this.) **A distinct failure mode worth knowing, found live**: the shared-folder *mapping itself* can point at the wrong host directory entirely (e.g. a stale worktree path from earlier work) — this presents identically to a caching problem (files that should be visible aren't) but isn't one; `prlctl list <vm> --info | grep -A2 "Host Shared Folders"` confirms the actual mapped path before assuming it's stale-cache flakiness rather than a wrong mapping. Together these turn "regression: re-run the full corpus on every add-in change" from an aspiration into something actually scriptable: restart the VM or just Revit between runs, wait for the add-in's reconnect loop (§05) to re-establish over the shared drive, then fire the corpus.

### Competitive coverage floor

Beyond tutorial-sourced cases, the corpus explicitly includes one task per fixed tool exposed by every surveyed fixed-catalog competitor (§03) — starting with the two broadest published tool surfaces among them. Each becomes a task phrased at the same level ("get all door widths on level 2," not "call door-width tool") and run against `execute_script` + discovery only. The bar isn't matching their tool list — it's confirming `execute_script` can reach every capability a fixed-tool competitor hard-coded, without the MCP Server ever needing an equivalent hard-coded tool of its own. Any task that fails here is a real API-discovery gap, not just a missing tutorial case, and gets priority over newly-sourced cases.

## 14. Open questions & design gaps

### Original open questions

The first five gaps below were identified while first drafting this PRD and resolved before the adversarial review further down ever ran. A sixth was added later, from live research rather than drafting or that review, and is still open rather than resolved — see its own status marker.

**Non-Revit-framework modal dialogs** *(resolved)* — Two-stage plan (see §07): v1 ships timeout + window-inventory diagnostic only, no auto-action (since #149, a pending answer whose inventory was dropped by the #138 wire-budget cap says so with a `window-inventory-skipped` notice rather than carrying nothing). v2's allowlist-based auto-dismiss has now shipped its mechanism with its first entry (the `#32770` "Virtual Memory - High Usage" box, #134) — sequenced deliberately so the heuristics are built from observed cases, not guessed.

**Long-running or runaway scripts** *(resolved)* — `execute_script` takes an optional `timeout_ms`; on lapse it returns `{status:"pending"|"running", execution_id}` instead of hanging, and `poll_execution` is called until the script completes (see §06). A second `execute_script` against a still-busy instance returns `{status:"busy", execution_id}` rather than queuing silently.

**Startup ordering & broker restart** *(resolved)* — One reconnect loop (§05) covers first-startup, Revit-before-broker, broker-before-Revit, Revit-with-no-broker-ever, and broker-crash-and-restart alike; a ring buffer of recent execution results lets `poll_execution` survive a broker restart. Concurrent Claude sessions are handled with a lock-or-proxy singleton: one broker process binds the port and routes, others proxy their stdio traffic through it rather than contending for the port.

**Document identity for the workspace key** *(resolved)* — Four states, four sources (§09): saved standalone → hashed local path; saved workshared → hashed *central* model path, never the local copy's path; unsaved/detached-not-yet-saved → session-scoped `tmp-` GUID; family documents follow the same rule as their saved state. First save promotes a `tmp-` ID to a `doc-` hash by renaming the workspace folder in place, with a short-lived alias so in-flight references don't just 404.

**Marketplace review vs. arbitrary script execution** *(researched, still genuinely open)* — Official APS Revit publisher guidelines say nothing explicit about scripting, custom code, eval, or sandboxing — the only relevant clause is a general stability requirement, and review mechanics beyond that aren't public. No case of a submission being rejected *or* approved specifically for code-exec was found either way. But the surrounding pattern is a real signal: every marketplace-listed AI-agent connector surveyed (§03) — including Autodesk's own official first-party entrant — sticks to fixed, mostly read-only tool catalogs and avoids arbitrary execution entirely, and the closest general-purpose scripting precedent was never submitted to the Marketplace at all (§12). Reading: no rule forbids it, but nothing resembling it has been tried, and Autodesk's own product choice leans away from it. **Plan:** treat Marketplace listing as optional rather than a target v1 must clear — independent signed-installer distribution (§12) is the durable path regardless of outcome; if a submission is attempted, be ready to offer a restricted/reviewed-mode fallback (e.g. a fixed high-level tool subset) rather than assuming full `execute_script` clears review.

**Real Revit API access from scripts** *(shipped)* — `ScriptGlobals.Document`/`UIApplication`/`UIDocument` are now the real `Autodesk.Revit.DB.Document` / `Autodesk.Revit.UI.UIApplication` / `UIDocument`. The narrow `IScriptDocument`/`IScriptUiApplication`/`IScriptUiDocument` interfaces are deleted, and the reflection-into-a-private-field workaround `skill.md` used to document is gone with them.

The earlier finding held up: no new transaction-ownership scheme was needed. `TransactionScriptExecutor`'s ambient `Transaction`/`TransactionGroup` already covers any write made through the real `Document` however a script obtained the reference. What the deleted interfaces actually guarded — `IDocumentAdapter.CreateTransaction`/`CreateTransactionGroup` — turned out to be the wrong target: those are *our own adapter methods*, not Revit API. (They were also described here as "unreachable from a script once `Document` is the real type" — **that was wrong, and is corrected under "Our own public types were a denylist bypass" below**.) The real invariant is a script constructing its own `Autodesk.Revit.DB.Transaction`/`TransactionGroup` (a `SubTransaction` is permitted — see below), and it is enforced by **`ScriptApiDenylist`** (`revit/mcp-bridge/src/MCPBridge.Core/Execution/ScriptApiDenylist.cs`): a semantic walk over the bound Roslyn compilation, run from `RoslynScriptRunner.GetOrCompile` at the same point as the existing top-level-`await` rejection, throwing `ScriptApiDenylistViolationException` (code `script-api-denied`). Because the ambient transaction is opened *before* compilation, a rejection unwinds through the identical rollback path as any compile error — no new failure handling.

Denylist shape, matching this section's original starting list but split into **two tiers by what the ambient transaction can undo**, which is the test that decides membership (§01's safety axis): *does a thrown exception actually undo this?*

- **Hard-blocked, no opt-in** — constructing `Transaction`/`TransactionGroup`. Not a risk judgement a caller may override: Revit permits one open `Transaction` per document and the executor already opened it, so a second one simply cannot work. Rejected during compilation, code `script-api-denied`. `SubTransaction` was in this list by association and left it (#146 Phase 1, #143): it fails the membership test in the other direction — it can only start *inside* the connector's open transaction, commits into it (so the §07 failure preprocessor still sees every write), and cannot escape the group's rollback — and it supplies the one thing the connector-owned model lacked, an intra-run savepoint. It is permitted **only as the resource of a `using`**: live, a sub-transaction still active when the enclosing transaction closed was accepted silently and Revit crashed on the next `Document.Close`; the connector cannot observe the script's object at runtime, so the syntactic walk requires the shape whose `Dispose` ends it.
- **Confirmation-gated** — `Document.Close`/`Dispose`/`Save`/`SaveAs`/`SaveAsCloudModel`/`SynchronizeWithCentral`/`Print`/`PrintToFile`; `PrintManager.SubmitPrint`; `UIDocument.SaveAndClose`; `UIApplication.PostCommand`; `WorksharingUtils.RelinquishOwnership`. These are *permitted*, but only when the `execute_script` request set `confirm_lifecycle_actions: true`. They are gated because each escapes the rollback boundary the ambient transaction provides — acting on a person's open session, the filesystem, the shared central model, a printer, or another user's checkout — so no exception undoes them. Refused runs get their own code, `script-lifecycle-confirmation-required`, naming every gated member the script used; resending the identical script with the flag runs it.

(Note this section previously wrote `SynchronizeWithCentralDocument`; the actual 2027 member is `Document.SynchronizeWithCentral`, confirmed via `describe_function`. The last five entries were added after an independent PR review proposed them: each was run through the membership question above and then confirmed to exist with those signatures in the live 2027 API via `describe_function` before being added — `Dispose` is `Close` under another spelling, and `PostCommand` is queued to run *after* control leaves the API context, i.e. after the ambient transaction has already closed, whatever command it names.) Keyed on *(containing type, member)*, not bare name, so ordinary `System.IO.Stream.Close` is unaffected. The connector's own `undo`/`redo` tools (#146 Phase 2c) post `PostableCommand.Undo/Redo` through this same `PostCommand` — deliberately not through a script: the tools carry their own gate (`confirm`, plus an optional expected `document_id` checked before posting) and report what was reverted afterwards, which a script calling `PostCommand` could never do, since the command runs after the script's own context has ended. The script-side gate is unchanged. As predicted, this is a starting point expected to grow from real use rather than an exhaustive policy over the ~1,700-type surface, and it is a guard against accidental damage, not a sandbox — reflection can still route around it, which is accepted. A gated member reached through a `dynamic` receiver (`dynamic d = Document; d.Close();`) falls in that same accepted bucket, for two reasons: nothing binds, so gating it would mean matching the bare name on any dynamic receiver — the check keying on *(containing type, member)* exists precisely to avoid that — and reaching for `dynamic` is deliberate rather than an accident. Constructing a hard-blocked type through `dynamic` is *not* accepted and does not work: confirmed live that every spelling (dynamic argument, all-dynamic arguments, target-typed `new`, dynamic result) is refused, because Roslyn still reports the bound constructor symbol; `Analyze` additionally falls back to the constructed *type* when a constructor symbol is missing, so the no-opt-in promise does not rest on that Roslyn detail alone.

**Both refusals reach the agent as their own `code`, with a `remedy`.** An independent PR review found they did not: `RequestDispatcher` reported every script failure with a hardcoded `script-execution-failed`, so `script-api-denied` and `script-lifecycle-confirmation-required` existed on the wire only as substrings of `message`, and the confirmation refusal — the one error in the connector with a completely mechanical next step — carried no `remedy` at all. Both now come from the exception itself (as does `script-await-not-allowed`, which reaches the same call site with the same gap); anything else keeps `script-execution-failed`, the honest answer for an arbitrary exception thrown by script code. Live-verified through the real broker, and pinned in both tiers on the record's actual `code` field — every existing assertion had matched the message text, which is exactly why this went unnoticed.

**Where the confirmation decision is made, and why not at compile time.** Compiled scripts are cached by verbatim text, but confirmation is a property of the *request* — the same script can arrive once without the flag and again with it. So the two halves are separated by what each depends on: DETECTION (which gated members a script's bound compilation touches) depends only on the text and is cached with the compilation (`ScriptApiAnalysis`, carried on `CompiledScript`); the DECISION is made per run in `RoslynScriptRunner.RunAsync`, after compilation and before anything is emitted or executed. That ordering preserves the property the compile-time checks already had — a refused run changes nothing and the ambient transaction rolls back through the existing path — while making a confirmed run unable to leave a cache entry that would wave a later *unconfirmed* run through.

Two implementation constraints worth recording, both found live rather than assumed. (1) The globals are lazy delegating properties, not values captured in `ScriptGlobals`' constructor: capturing eagerly would throw for every test fake and take the entire tier-1 suite down, not just the few tests that genuinely need a live document. (2) The raw objects come from separate `IRawDocumentSource`/`IRawUiApplicationSource`/`IRawUiDocumentSource` capability interfaces implemented only by the real adapters, *not* from members on `IDocumentAdapter`. A Revit-typed member on `IDocumentAdapter` forces the fakes to name a Revit type, which gives `MCPBridge.Core.Tests.dll` its own direct `RevitAPI` reference — and `RevitAPI.dll` is a mixed-mode C++/CLI assembly only Revit's native host can load. Measured consequence: `xunit.runner.visualstudio` could not resolve it, **skipped the entire test assembly, and `dotnet test` still exited 0** — 298 tests silently stopped running while the build looked green. Tests instead get Revit types bindable from script scope as Roslyn *metadata* references by path (`RoslynScriptRunner`'s `additionalMetadataReferencePaths`, unused in production, where Revit has already loaded them).

**Application-level access needed no new plumbing** *(shipped, zero code)* — `Application.NewProjectDocument`/`NewFamilyDocument` live on the top-level `Autodesk.Revit.ApplicationServices.Application`, one level above the three globals above, and were scoped as a fast-follow to this section on the assumption that `ScriptGlobals` would need a fourth delegating property and a fourth `IRaw*Source` interface. It needs neither. `UIApplication` is the real `Autodesk.Revit.UI.UIApplication`, `.Application` is an ordinary property on that real type, and nothing was ever built to wrap or block it — so the whole `Application` surface has been reachable from a script since this section shipped. Verified live against Revit 2027 before any implementation was attempted (`TestApplicationCreatesDocuments`, `revit/test-harness/`): `UIApplication.Application` reports `Autodesk.Revit.ApplicationServices.Application`, `NewProjectDocument(app.DefaultProjectTemplate)` returns a real, queryable `Document`, and `NewFamilyDocument` returns one with a usable `FamilyManager`. The lesson is worth more than the finding: a capability that falls out of a seam being genuinely wide is easy to spend a PR re-building, and the cheap check is to probe the live connector before writing the plumbing.

**Neither creation member is gated**, run through this section's own membership question. A freshly created, unsaved, in-memory document has nothing for an exception to fail to undo: it touches no file, no central model, no device, and no session a human has open. What escapes the rollback boundary is *persisting* it — and `Save`/`SaveAs`/`SaveAsCloudModel` are already gated in their own right, so the gate already sits exactly where the effect becomes irreversible. Adding creation to it would gate the harmless step and buy nothing.

**Two real limits came out of the same live pass, both narrower than they sound and both now pinned by tests.** First, *a created document was not covered by the ambient transaction* — `TransactionScriptExecutor` opened that on the routed document (the `document_id` the call names, which routes for real as of the v1 remediation series; before that, always the ACTIVE document), so writing to a newly created one threw `ModificationOutsideTransactionException`. Revit itself would allow a second `Transaction` for it (one-open-transaction is a per-*document* rule, confirmed live by constructing one reflectively: the write succeeded and committed), but `ScriptApiDenylist` check 1 refuses to construct `Transaction` at all, without regard to which document it targets. **This is now resolved — see "Writable created documents" below.** Second, *a created document has no `document_id` and cannot be given one* — **no longer true either**, as the v1 remediation series changed it; see below.

**Writable created documents** *(shipped, [issue #24](https://github.com/eichler-ai/connectors/issues/24))* — the connector now opens and owns a `Transaction`/`TransactionGroup` for every document a script creates, so a created document is writable without a script ever constructing a transaction. `ScriptGlobals` gains two script-facing helpers, `CreateProjectDocument(templatePath?)` and `CreateFamilyDocument(templatePath)`, which create the document *and* open its managed transaction in the same step; `TransactionScriptExecutor` generalizes from one `(TransactionGroup, Transaction)` pair to N, held in a new `ManagedDocumentTransactions`, with the ambient document opened before the run as before and created ones opened lazily as they appear.

**`ScriptApiDenylist` check 1 is unchanged — that is the point of this shape, not a side effect.** The rejected alternative was a runtime document-identity comparison, ruled out because Revit hands back different wrapper objects for "the same" document depending on the API entry point (§09's own gotcha) and `DocumentIdentity.ResolveCached` is weakest for exactly the unsaved documents this case is about — a naive same-instance check would have reopened the bypass class two independent review rounds already closed in that file. The creation helper is an ordinary method call on `ScriptGlobals`, not an object creation, so the denylist's semantic walk has nothing new to bind to; asserted at both tiers rather than assumed. Robustness reasoning, recorded because it drove the choice: if this plumbing has a bug the failure mode is a broken *feature*, not a broken security boundary. **The raw `Application.NewProjectDocument`/`NewFamilyDocument` path is unaffected and stays read-only** — both paths work, and that is the only difference between them.

**Writing to a document a PRIOR `execute_script` call created — adoption, a third member of this same unconditional-allow tier** *(shipped as `Connector.OpenForWriting`; since #146 Phase 3 a `Connector.WithTransaction` block on an untracked document performs the same adoption itself, and `OpenForWriting` is removed — read it below as "a block on that document")*. A created document's managed transaction commits and closes the moment the call that created it returns; a LATER, separate `execute_script` call that finds the same document via `Application.Documents` (by Title — no `document_id` exists, see above) can read it freely but not write to it, for exactly the reason check 1 exists: nothing opened a transaction for it in this run, and a script may never open one itself. Found live while building the test-harness coverage corpus's fixture system, which specifically needs this (one document, built up across several independent subtests/calls). `ScriptGlobals.OpenForWriting(document)` opens a managed transaction on an EXISTING document the same way `CreateProjectDocument`/`CreateFamilyDocument` do for a new one — same rollback-on-throw/commit-on-return guarantee, same "ordinary method call, not an object creation" invisibility to check 1, no `confirm_lifecycle_actions` gating needed under the same governing test. New: `ManagedDocumentTransactions.Open` now guards against opening the same document twice in one run (by `DocumentId`, never `ReferenceEquals`) — a real, script-triggerable case `OpenForWriting` introduces that `CreateProjectDocument`/`CreateFamilyDocument` never could (they only ever hand back a document nothing else could already reference). **That guard's known limitation is now closed for unsaved documents too** *(v1 remediation series)*: `DocumentId` once could not distinguish-or-match two different wrapper objects for the same live document (the `Application.Documents` vs. `ActiveUIDocument.Document` gotcha; an earlier reference-equality backstop was provably dead code for the same reason and was removed), so the double-open guard was only reliable for saved documents. With §09's unsaved identity now title-derived and wrapper-independent, the same-document comparison holds across wrappers for every open document, and the guard's signposted refusal — not Revit's raw one-transaction exception — is what surfaces a double-open.

**A deliberate scope expansion, recorded rather than left implicit**: adoption lets a script write to *any* open document it can name via `Application.Documents`, not only the one routed by `document_id` — the same governing "does a thrown exception undo this?" test that exempts `CreateProjectDocument`/`CreateFamilyDocument` from `confirm_lifecycle_actions` also exempts this, since rollback-on-throw covers it identically. Decided, not accidental: this is a real widening of what one `execute_script` call can touch (previously bounded to the routed document plus whatever the script created this run), and an agent could in principle adopt and write to some *other* open document than the one it was asked to operate on. Left ungated for now, matching this tier's existing precedent; revisit if that widening turns out to matter in practice.

**The connector's API is an add-in API, and is discoverable as one** *(shipped, [issue #91](https://github.com/eichler-ai/connectors/issues/91))*. The connector-provided members above — `Publish`, `ExportsDirectory`, `ImportsDirectory`, `WithTransaction`, `Settle`, `CreateProjectDocument`, `CreateFamilyDocument`, `DialogResultOverrides` — are reached from a script through a single `Connector` global (`Connector.Publish(path)`), typed `Eichler.Connectors.Revit.Connector` and shipped in its own assembly whose only public type is that one. §08's discovery indexes it as `kind = 'addin'`, so it appears in `list_functions`/`search_functions`/`describe_function` beside Autodesk's own API, with signatures and summaries generated from XML doc comments beside the code.

The problem this solves is not that the members were hard to call — it is that nothing told an agent they are **ours and not Revit's**, and that five places enumerated them by hand (`skill.md`, this document, `tools.md`, `execute_script`'s tool description, `ScriptGlobals`) with three already disagreeing. A namespace beside `Autodesk.*` carries the provenance signal at no cost, and generating the list from the code removes the surface that drifted. The mechanism was not new: §08 already indexed third-party add-in assemblies and already promised add-in APIs stay searchable — the connector had simply excluded itself from it.

`Document`, `UIApplication`, `UIDocument` and `CancellationToken` deliberately stay bare globals and are **not** moved under `Connector`. They are Autodesk's objects handed into scope, not connector functions; filing `Autodesk.Revit.DB.Document` under a connector namespace would assert the opposite of what this change exists to signal. §06 also publishes those three names as an external contract.

**Our own public types were a denylist bypass, and it was live-exploitable** *(found by independent review of the issue #24 PR; fixed)*. `RoslynScriptRunner.LoadableReferences()` references every assembly loaded in the Revit AppDomain, which includes `MCPBridge.Core.dll` and `MCPBridge.RevitAdapter.dll` — so every `public` type in them was nameable and constructible from an agent script. Confirmed against real Revit 2027: a script called `UIApplication.Application.NewProjectDocument(...)`, wrapped the result in `new MCPBridge.RevitAdapter.RevitDocumentAdapter(raw)`, called our own `CreateTransaction`, started it, created a `Level` and **committed it**, reporting `status: "success"`. `ScriptApiDenylist` never fired and structurally could not: the `new Autodesk.Revit.DB.Transaction(...)` executes inside our adapter, while `Analyze` only walks the script's own compilation. The same shape against the *ambient* document was blocked only by Revit's own one-transaction-per-document rule — incidental, not a guard the connector was applying. This predates issue #24 (`RevitDocumentAdapter` has been reachable since Phase 3), but issue #24 added a second, strictly more powerful instance of the same pattern in `ManagedDocumentTransactions`, which owns commit/rollback for every managed document.

**Fixed structurally rather than by extending the denylist**: `RevitDocumentAdapter`, `RevitUiApplicationAdapter`, `RevitUiDocumentAdapter`, `RevitTransactionAdapter`, `RevitTransactionGroupAdapter` and `ManagedDocumentTransactions` are now `internal` (with `InternalsVisibleTo` for `MCPBridge.Core.Tests`), so a script cannot name them at all. Adding them to `DeniedConstructedTypes` was the alternative and was rejected: that table is meant to stay small and Revit-API-focused, and a list of forbidden names is only ever as complete as the last person to remember to extend it. The change cost nothing structurally — every public member already returned the `IDocumentAdapter`/`IUiApplicationAdapter` interfaces, which were left public at the time, so no assembly outside those two referenced the concrete types. **The general rule this establishes: in `MCPBridge.Core` and `MCPBridge.RevitAdapter`, `public` means "script-reachable".** Reflection still reaches these, unchanged and still accepted (§01: this is a guard against plausible mistakes, not a sandbox). Pinned by `revit/test-harness/denylist_bypass_test.go` — tier 2 by construction, since `internal` only means anything against the assemblies as Revit actually loads them.

**A second instance of the same bypass class survived that fix, and it invalidates the rule as first written** *(found by a second independent review round of the same PR; fixed)*. The round-1 wording said interfaces were safe to leave public because "a script can name `ITransactionAdapter` and still never obtain one once every implementation is internal." That is false. `RevitScriptExecutionHandler` was a `public` type with a public constructor and a public `Execute(UIApplication)` whose whole body is `_callback.OnExecute(new RevitUiApplicationAdapter(app))` — a public factory handing the now-internal adapter, typed as the still-public `IUiApplicationAdapter`, to **arbitrary caller-supplied code**. A Roslyn script submission can declare types, so a script supplies the `IScriptExecutionCallback` itself, captures the adapter, casts it to `IDocumentCreationSource`, creates a document and calls `CreateTransaction` on it — a real, unmanaged, untracked transaction, reached **without naming a single internal type**. It also reached `ActiveUiDocument.Document.CreateTransaction(...)` on the *ambient* document the same way, stopped again only by Revit's own one-transaction-per-document rule (with `CreateTransactionGroup` not even covered by that incidental protection). Note also that explicitly implementing `IExternalEventHandler.Execute` privately would not have fixed it: `IExternalEventHandler` is a public Revit SDK interface a script can cast to.

**Restated rule, and the durable fix.** A `public` type in these assemblies must neither **be** an adapter/adapter-producing type **nor return or yield one** — directly, or through a caller-supplied callback or delegate. Reviewing a signature is not enough; what a member's *body* passes outward is part of its surface. Rather than making only `RevitScriptExecutionHandler` internal (which would have closed this instance and left the class open for a third), the adapter **interfaces** themselves are now internal too — `IDocumentAdapter`, `IUiApplicationAdapter`, `IUiDocumentAdapter`, `IDocumentCreationSource`, `ITransactionAdapter`, `ITransactionGroupAdapter`, `IScriptExecutionCallback` and the `IRaw*Source` trio — with `InternalsVisibleTo` threaded `MCPBridge.RevitAdapter` → `MCPBridge.Core`/`MCPBridge.AddIn`/`MCPBridge.Core.Tests` and `MCPBridge.Core` → `MCPBridge.AddIn`/`MCPBridge.Core.Tests`. That pulls `ExternalEventBridge`, `TransactionScriptExecutor` and `RequestDispatcher`'s constructor internal with them, which is the cost; the benefit is that the capability is *unnameable* from script scope rather than merely un-constructible one type at a time. `ScriptGlobals` deliberately stays public (Roslyn binds a script's globals by that type) with an internal constructor, exactly as before. Pinned by a new tier-2 case, `TestConnectorCapabilitiesAreNotReachableThroughACallback` — the round-1 cases all assert `new <ConcreteType>()`, which is precisely why they kept passing while this hole was open.

**A third review round found no third transaction-boundary bypass — the two it did find are lower-severity siblings, and both were live-exploitable** *(fixed)*. Check 1 held in every shape tried (dynamic/reflection sweep, public events, a closing sweep over the assemblies), which is the material result. What did not hold was the *confirmation-gated* tier and the dialog machinery beside it:

- **A script could self-grant `confirm_lifecycle_actions`, with no reflection and no internal type named.** `ScriptGlobals` must stay public and `Delegate.Target` is public on every delegate, so `((System.Action<string,string>)Publish).Target` handed a script the live `ScriptGlobals` object (that exact spelling no longer compiles since [issue #91](https://github.com/eichler-ai/connectors/issues/91) moved `Publish` behind `Connector`, and the `Delegate.Target` route to `ScriptGlobals` is gone with it — every public instance member of `ScriptGlobals` is now a property, so there is no method group to convert. `RoslynScriptRunner` being `internal` remains the thing that closes this); `RoslynScriptRunner` was then public, with a public `RunAsync(..., bool confirmLifecycleActions = false)`, so the script started a **nested run** passing `true` — letting the *script*, not the *request*, decide the tier that exists precisely to require a request-level opt-in. Confirmed live against Revit 2027: a call that never set the flag ran a nested script binding `Document.Save` and reported `status: "success"`. Check 1 was never affected (the nested compile still runs the full `Analyze`, which refuses transaction construction unconditionally). Fixed by making `RoslynScriptRunner` `internal` — its only production caller, `TransactionScriptExecutor`, is already internal — pinned by `TestConfirmationTierCannotBeSelfGranted`.
- **`ActiveDialogContext` was a public static class with public mutators.** `ClearActive()` mid-script switched dialog auto-suppression off (`DialogSuppressionHandler` answers only while `IsActive`), so the next real modal dialog would display and block the very UI thread the script runs on — a one-line denial of service with no guarantee a human is present to click it; `DrainRecorded()` mid-script emptied the recorded notices before the executor collected them, erasing the §01 record of which dialogs were auto-answered (observed live erasing a real one). The whole class is `internal` now, read-only members included — nothing outside `MCPBridge.AddIn`/`MCPBridge.Core.Tests` wanted them, and the rule above says a public type here is a script-reachable one. Pinned by `TestScriptCannotTamperWithDialogSuppression`, with `TestDialogsAreStillAutoSuppressed` pinning that suppression itself still works across the `InternalsVisibleTo` seam rather than only that the tampering stopped compiling.

Both are the same *class* as rounds 1 and 2 — a public surface in these assemblies handing script scope something it should not have — reached one rung down from the transaction boundary rather than at it. The reflection carve-out was also restated where it is documented: reflection reaches the **connector's own** internals, not just Revit's API, and over `ManagedDocumentTransactions` that means commit/rollback authority on every managed document including the ambient one. That was already the recorded position here and in that class's own comment; `ScriptApiDenylist`'s comment now says so too, since it had described only the smaller "reach a denied Revit member" case.

**Commit semantics across N documents.** The script never commits or rolls back anything, with N documents exactly as with one: every commit happens in the executor after the script's own code has finished, and the script's return-or-throw governs all N uniformly. Order is deliberate — created documents first, in creation order, then the ambient document **last**. A committed Revit transaction cannot be un-committed, so ordering is the only lever over what a partial failure can damage, and committing the ambient document last means a failure among the created ones is still answerable by rolling the human's real open model back. What can then survive is confined to unsaved, in-memory scratch documents that touch no file, no central model and no session. When that happens the run is reported as failed *and* carries a `script-partial-commit` notice naming exactly which documents kept their changes and which did not — never a silent partial outcome (§01).

That notice reports **three** states, not two, following an independent review finding that it was overclaiming: `committed_documents`, `rolled_back_documents`, and `unknown_state_documents`. Rollback is best-effort and swallows exceptions by design (a rollback failure must never mask the original commit failure, nor stop the next document's rollback) — but the first implementation added every document to the "rolled back" list *regardless of whether its rollback threw*, so a document whose own rollback failed was reported as cleanly undone. That is a false claim in precisely the report that exists to be honest, and the ambient document — a human's real open model — is one it could be made about. Rollback still swallows; what changed is that its outcome is now observed and reported. An unknown-state document also makes the run "partial" on its own, even with nothing committed, so it always produces a notice: dropping it from both lists would be the silence §01 forbids, in the case that most needs a voice. Relatedly, `ManagedDocumentTransactions.CommitAll` documents that it never throws, and its `ITransactionAdapter.CommitFailures` reads sat outside every `try` — an adapter getter that threw escaped the method after its entry list had already been cleared, silently disarming the executor's `finally` rollback net and leaking every not-yet-committed document's transaction into the live session. Those reads are now guarded (an unreadable failure list is itself reported as an error-severity failure) and the entry list is cleared **only on the normal return path, deliberately not in a `finally`** — a `finally` runs on the exception path too and would disarm the net just the same — so an unanticipated escape leaves the executor's `finally` something to work with.

A second review round then found that `CommitAll`'s "never throws" contract was still overclaimed: three `entry.Describe()` calls in `CommitInOrder` bypassed the `SafeDescribe` helper sitting two methods away, and `Describe()` reads `Document.Title`, a live Revit call. When it threw *after* a successful commit, the exception escaped `CommitAll`, escaped `TransactionScriptExecutor.ExecuteAsync` (whose `try` has a `finally` but no `catch`) and surfaced as a raw unhandled exception — destroying the `script-partial-commit` notice that names which documents committed, i.e. exactly the information the notice exists to carry. All three now route through `SafeDescribe`, so a document that cannot name itself is still reported, under a placeholder. In the same round, the notice's own wording was corrected: it is also emitted when the *first* document fails and its rollback throws, where `committed_documents` is empty, and it still read "…failed to commit after 0 other document(s) had already committed … so those changes remain" — claiming surviving changes that do not exist, in the one notice whose entire job is honesty about partial state. That clause (and the two inspect-what-committed remedies) is now conditional on something actually having committed.

**How reachable is that partial failure, actually? Investigated live rather than assumed, and the answer is "barely, but not provably never".** Four routes were tried against Revit 2027. (1) *Invalid input* — duplicate level names, duplicate elevations, deleting every level out from under a wall: Revit validates at the API CALL, throwing `Autodesk.Revit.Exceptions.ArgumentException` immediately, which fails the whole script and rolls every document back uniformly. No partial state is reachable this way. (2) *Failures-API postings* — confirmed live that the per-document Failures API genuinely reaches created documents (an overlapping-walls warning and a room-not-enclosed warning raised inside a script-created document were auto-dismissed and surfaced in `notices[]`), so the mechanism is wired; but every failure that could be synthesized in a blank project document was WARNING-level, which commits. An ERROR-level posting would force that one document's rollback and is therefore the one genuinely plausible route. (3) *Closing a document mid-script* — the obvious way to make a later commit throw, and **Revit itself refuses it**: `Document.Close` returns *"Close is not allowed when there is any open sub-transaction, transaction or transaction group."* Because the connector now holds a transaction on every created document, a created document is un-closable for the duration of the run — the same rule the ambient document has always been under. That is a real, if small, behaviour change (the raw `NewProjectDocument` path, having no transaction, still permits `Close`) and it removes this route entirely. (4) *`Assimilate` throwing after a good commit* — handled in code, not reproducible on demand. **Conclusion:** the honest position is that partial commit is not demonstrable today but is not structurally impossible either, so it is implemented and reported rather than assumed away — which is what §01 requires. All four findings are pinned by `TestCreatedDocumentIsWritable` where pinnable.

Second, *a created document has no `document_id` and cannot be given one*. This changed with the v1 remediation series, in two steps that compose: `register`'s document list is live (§05, the `DocumentCreated` push), and unsaved identity is title-derived and wrapper-stable (§09) — so a created document now DOES appear in `list_instances` with a routable `tmp-` id moments after creation, and a later `execute_script` can address it by that id like any other open document. In-script addressing by `Title` (below) still works and remains useful within the creating run itself; it is no longer the only option across runs. A script cannot change that either: `UIApplication.OpenAndActivateDocument` throws *"The active document is currently modifiable"* from inside the ambient transaction — as `Autodesk.Revit.Exceptions.InvalidOperationException`, not `System`'s. Worth naming, because the two share a short name: `ex.GetType().Name` reads identically for both, so catching the wrong one fails with the exact message you were looking for. **That refusal is about the ACTIVE document, not the created one, and is therefore routable around** *(verified live, Revit 2027, issue #118; since #146 Phase 3 the active document is not modifiable outside a `WithTransaction` block, so activation from a script now needs no routing at all — it is refused only inside a block on the active document, and the "three calls" below collapse to two: create + `Settle` + `SaveAs` in one run, activate in the next)*: a call routed at document B leaves the *active* document A unmodifiable, and `OpenAndActivateDocument` then succeeds. So a script-created document can be made genuinely visible to a person — but it takes **three calls**, not the "three steps" the issue suggests, because `SaveAs` is blocked in the creating run for the same reason `Close` is (below) and `OpenAndActivateDocument` needs a path: create, then `SaveAs` from a second call, then `OpenAndActivateDocument` from a third routed at any document **other than the currently active one**. Stated that way deliberately — "a script cannot activate from inside its own transaction" would be the tempting general rule and it is false; the bar is only that the *active* document is modifiable, which routing elsewhere avoids. Both directions verified: refused from a call routed at the active document, succeeded from one routed at a background document with the same two documents open. (The raw `NewProjectDocument` path has no managed transaction and *can* `SaveAs` in its own run, which collapses it to two.) Deliberately not wrapped in a `Connector` member: a created document is headless by design (no window, never active, invisible to whoever is using Revit), which is what makes it safe to write to without disturbing the human's session, and stealing their focus should stay an explicit act rather than a side effect of "create a document". What does work, and is the sanctioned answer for §13's fixture system, is **in-script addressing**: a created document stays in `Application.Documents` for the rest of the session, so a later `execute_script` call finds it there by `Title` or `PathName`. No new identity concept is needed for it, and none should be invented until per-document routing exists.

**The managed transaction blocks `Close` AND `SaveAs`, for exactly the creating run — and issue #114's proposed `Connector.DiscardDocument` is therefore declined** *(declined for #114's own case; the mechanism is reopened for a different one — see §06's `settle-on-request` and the paragraph below)* *(all verified live, Revit 2027)*. `CommitAll` closes every managed transaction when the script returns, so from the very next `execute_script` call the document is ordinary: `Close(false)` and `SaveAs` both succeed under `confirm_lifecycle_actions`. Confirmed for a blank project document, a family document, a scratch one dirty with levels/walls/rooms, and — the case the recipe can actually reach — a *saved, on-disk, modified* document; no `notices[]` were raised on any of them, so no dialog fired and none was auto-answered.

This resolves all three symptoms #114 reported, not just `Close`. `SaveAs` in the creating run does fail with the reported *"Unable to close all open transaction phases!"* — it is the same one-transaction rule, and the same next-call fix. (The raw `NewProjectDocument` path, having no managed transaction, saves in its own run.) Route (3) above already said "for the duration of the run"; `skill.md` dropped that qualifier and told agents there was *no* cleanup path at all, they believed it, and that is where #114's five orphaned documents came from. A same-run discard buys one round trip against a new public member on the one type that is the whole script API's attack surface, plus mid-run release semantics in `ManagedDocumentTransactions` — the documentation was the defect. The remaining gap is the **error path**: a script that throws leaves its created documents open having never returned their titles, so `list_instances`' `tmp-` ids are the only handle. Emitting created-document identities as a notice on every run would close that properly and costs no public surface; filed as [issue #122](https://github.com/eichler-ai/connectors/issues/122) rather than smuggled into a docs fix.

**That decline stands for #114's own case and is reopened for a different one** (§06, `Connector.Settle`). It was correct that a same-run *discard* buys only a round trip, because #114's symptom had a documentation fix. It does not generalize: `Connector.Settle` is the same "mid-run release semantics" this paragraph declined, but it is now buying three capabilities that exist at **no** price today — stairs (#115, unreachable by any script-reachable path), `LoadFamily` and the not-modifiable-target family without a two-call split, and `Save`/`SaveAs` in the creating run. The cost-benefit that made "one round trip" decisive does not survive that change, so the mechanism is reconsidered on the new evidence rather than treated as settled by this paragraph.

### From adversarial review

An independent adversarial pass (Aug 2026) surfaced ten further findings, tracked here and resolved in the same one-at-a-time process as the original five.

1. **Local vs. remote topology was unspecified** *(resolved)* — The reverse-dial argument (§05) needs the VM to reach a non-loopback host address; §10's "loopback-only" rule and file-based discovery both assumed same-machine. Now split into an explicit **local mode** (default; loopback bind, file discovery — the real target deployment) and **remote mode** (opt-in; configured host:port, non-loopback bind on a specific interface, broker builds for macOS too). Remote-mode authentication is resolved by finding 5's broker-minted token riding the shared drive.
2. **No cancellation for runaway scripts** *(resolved)* — Cooperative `CancellationToken` in script globals plus `cancel_execution` (§06) handles well-behaved scripts; `max_duration_ms` auto-triggers it so an unpolled script doesn't run forever unnoticed. For scripts that don't cooperate, a grace-period fallback marks the instance `unrecoverable` rather than leaving the agent polling a dead end — recovery is a plain Revit restart, which mints a fresh instance_id.
3. **Dialog suppression missed the Failures API** *(resolved)* — An `IFailuresPreprocessor` on every script transaction (§07) auto-dismisses warnings, rolls back and surfaces errors as a real script failure, and always reports what it touched — never silent, per the observability principle (§01). A confident-auto-resolve mode for specific recurring errors is deferred until real usage shows which ones recur, mirroring the non-framework-dialog v1/v2 split.
4. **File exchange exposed paths, not content** *(resolved)* — Shared filesystem is now the primary mechanism (§09) — a mapped drive with an agreed root-path pair in remote mode (also now backing broker discovery, §05), automatic in local mode — with the broker rewriting paths into agent-host-native form so the agent's own filesystem tools do the I/O outside MCP entirely. A chunked `read_file` is the fallback for no-shared-filesystem setups. Confirmed Claude Code supports MCP resources, but its 25,000-token default output ceiling rules them out as the large-file mechanism regardless — validates shared-filesystem-first rather than resources-first.
5. **Singleton/token design authenticated nothing** *(resolved)* — The broker (not the add-in) now mints the token on becoming primary and writes it into `broker.json`; every add-in and secondary agent-client proxy must present it (§05/§10). Honestly scoped rather than overclaimed: in local mode it only filters accidental cross-talk (same-user processes can still read `broker.json`), but in remote mode it's the real protection, bounded by who has access to the shared drive it now rides on (§09).
6. **ExternalEvents don't always fire** *(resolved)* — New `pending` status (queued, UI thread not yet free) is now distinct from `running` (§06), surfaced in `poll_execution` and `list_instances`. §07's v1 fallback no longer claims a follow-up script can act on a stuck dialog — it's diagnosis-only by design, since any remedy has to run off the UI thread entirely, which is exactly what v2's allowlist auto-dismiss already does.
7. **Roslyn-in-process assembly collisions and memory growth** *(resolved)* — A dedicated collectible `AssemblyLoadContext` (§06) isolates MCP Bridge's own Roslyn dependencies from other add-ins' bundled versions, and each execution's compiled script loads into its own short-lived ALC that's unloaded on completion — bounding memory growth instead of retaining every unique script for the session, with a small LRU for genuine re-runs.
8. **Discovery commands' execution locus and response size were unspecified** *(resolved)* — Reflection doesn't touch the Revit API context, so it never needed `ExternalEvent` — served live on the add-in's background connection thread, discovery is simply never subject to §06's busy/pending state at all (§08). Accepted trade-off: needs at least one connected instance, no persisted index. Bounded pagination (~50 for `list_functions`, ~20 for `search_functions`) is sized against Claude Code's confirmed 25,000-token MCP output ceiling (§09). A precomputed function-graph index for `list_functions` is deferred to real usage, not designed now. **Real-usage gap found and fixed**: this index covers every assembly loaded in the process, add-ins included (deliberate — an agent can validly call another add-in's public API, not just Revit's own), which on a real dev VM is 690 namespaces, mostly third-party noise; `search_functions`/`list_functions` now rank/sort core (`RevitAPI`/`RevitAPIUI`) results first as a tie-break, never excluding add-ins, just no longer letting them bury core results by sheer volume.
9. **Core bet validated last, not first** *(resolved)* — Flagged by the review as the single biggest project risk, reasoning from the doc alone. In practice this is substantially de-risked already: prior experience building execute_script-like capability against Revit informs the confidence behind this design, which a fresh review reading only the PRD text has no way to see. Phase 04 stays where it is — no forced pre-infrastructure spike — but the corpus's job (§13) is unchanged: it's still the thing that would surface a gap if one exists, and the deferred example-corpus idea (§08) remains available to pull forward if phase 04 results call for it.
10. **Document-identity edge cases** *(resolved)* — Two instances sharing one central model's workspace is correct-by-design; the fix was giving `tmp/` a per-instance subfolder (the only un-timestamped directory) and surfacing shared `document_id`s in `list_instances` (§09). Linked models deliberately get no top-level identity — reached through the host document's own script globals, not addressed directly. A real heartbeat now backs the `status` field, with a distinct `unresponsive` state separate from execution-driven `unrecoverable` (§05).

## 15. Phased roadmap

1. **Core loop, Revit 2027 only.** *(done)* Add-in with TCP client and startup/reconnect loop; Go broker (official MCP SDK, stdio transport) built for both local and remote mode (§05), with singleton lock-or-proxy plus broker-minted token auth for concurrent sessions, `execute_script`/`poll_execution`/`cancel_execution` over the NDJSON transport, ExternalEvent threading with a per-execution collectible `AssemblyLoadContext`, unsigned dev build. Success: a script written by an agent can create/modify/query elements in an open document and get a JSON-RPC result back, including a long-runner that's polled to completion and a deliberately-cancelled one that rolls back cleanly, surviving a broker restart mid-run, with memory reclaimed after each unique script.
2. **Dialog suppression & multi-instance.** *(done)* `DialogBoxShowing` handler with default-safe auto-answer policy; `IFailuresPreprocessor` for transaction warnings/errors with structured reporting; `pending`/`running` status distinction; timeout + window-inventory diagnostic (diagnosis-only in v1) fallback for non-framework dialogs; instance registry, heartbeat-backed `list_instances` with two-plus concurrent Revit instances on the same central model validated live; per-document `{instance_id, document_id}` routing landed later, in the v1 remediation series (with a loud `document-not-found` + candidates error, `UIDocument` null for a routed background document, and the workspace following the routed document), alongside live document-snapshot push (issue #30). **Known gap found since**: the dialog-suppression mechanism only covers dialogs a script's own transaction triggers — two real dialogs that fire during document *open* (a link-reload warnings summary, "File Opened By Another User") sit outside that wrapper entirely and still need a human, discovered live this session.
3. **API discovery.** *(mostly done)* Add-in serves `list_functions`/`search_functions`/`describe_function` via live reflection over `RevitAPI.dll`/`RevitAPI.xml` on its background connection thread, with pagination, independent of §06's busy/pending state. Structured file exchange directory implemented and wired into script globals, keyed by the `doc-`/`tmp-` document-identity scheme with save-time promotion. **Still open**: path rewriting for the shared-drive remote-mode case (the discovery-file-location split exists via `-app-data-dir`, but no path rewriting beyond that) and chunked `read_file` as the no-shared-filesystem fallback — neither exists yet (§09).
4. **Validation corpus.** *(in progress)* The tutorial-workflow corpus itself (15–20 cases, beginner through advanced) is underway — see `revit/docs/validation-corpus.md` for the grading protocol, the case list, and per-case status (1/15 done as of this writing). What blocked it — no *sanctioned* way for a script to reach real Revit API elements, only an unsupported reflection workaround a corpus should never depend on — is resolved: see §14's "Real Revit API access from scripts", shipped some time ago. The corpus is built on `ScriptGlobals.Document`, graded on whether the discovery tools alone are enough for an agent to self-teach each task, distinct from `revit/test-harness/`'s existing Phase A/B/C bundles, which are valuable regression coverage of the connector's own plumbing but were authored knowing the answer rather than produced by discovery-only research — see the corpus doc's own "Relationship to `revit/test-harness/`" section. The §13 "competitive coverage floor" (one task per fixed tool in the broadest surveyed competitor catalogs) is separate and not yet scoped.
5. **Signed distribution.** *(pipeline built, deliberately unsigned-for-real)* `install.ps1`/`install-mac.sh` were already built against a local test payload (`-LocalPackagePath`); a real `.github/workflows/release.yml` now runs on a self-hosted Windows runner, builds both TFMs plus the broker, signs both, packages `mcpbridge-release.zip` + `checksums.txt`, and publishes a real GitHub Release on every `v*` tag push (a `/release major|minor|patch` command drives the whole cut-and-tag flow). Signing is deliberately **self-signed, not a real CA certificate** — the cost and identity verification of a real one (individual or business) is deferred until the product is fully released; a self-signed signature is genuine Authenticode but Windows still shows "Unknown Publisher" until that swap happens. The swap itself is contained to the workflow's signing step alone.
6. **Multi-version + Marketplace.** *(2025 done)* Added the `net8.0-windows` TFM for Revit 2025 alongside 2027's `net10.0-windows`, cross-built by the single installed .NET 10 SDK (no second SDK — it restores the net8.0 targeting pack via NuGet), plus discovery-API multi-version disambiguation: an unscoped `list_functions`/`search_functions`/`describe_function` call errors (`ambiguous-instance-version`, with candidates) when connected instances span more than one Revit version instead of silently picking one, and every discovery response now carries which `revit_version` it reflects (§08). Live-validated against real, simultaneously-connected 2025+2027 instances. 2026 TFM and per-version manifests remain open — 2026 is genuinely unverified (not installed on the dev VM); don't assume it matches 2025 just because they're adjacent releases (§11). Marketplace submission is attempted but not required for success at this phase (§14) — independent signed distribution continues either way; if `execute_script` doesn't clear review, submit a restricted read-mostly tool subset instead, matching the pattern every other marketplace AI-agent connector already follows.
7. **Allowlist-based dialog auto-dismiss.** *(mechanism + first entry shipped, #134)* Field usage surfaced the first recurring non-framework dialog (#129); the window-inventory fallback now auto-dismisses the `#32770` "Virtual Memory - High Usage" box via `WM_CLOSE`, reported in `notices[]`. The allowlist stays open to further live-verified signatures.
